# Deep Research：为什么那么多人用 React / Next.js —— 并严肃质疑「SSR/SEO 是 Next.js 核心卖点」

> Generated 2026-10-28 至 2026-10-29 | Depth: deep | Sources: 70 | 语言：中文（检索词中英并行）

## TL;DR

React 赢的不是"技术最好"，而是**在正确的时间点上拿到了最广的复用面**（原生 App、跨端、组件生态、以及后来的 LLM 训练数据），然后用"局部解"策略把生态滚成飞轮；Next.js 赢的是**React 官方文档把新项目入口指向了框架，而它是唯一把 RSC 完整实现出来的那一个**，加上 Vercel 的商业推力 [13][8][38]。「SSR/SEO 是核心卖点」这句话**一半是历史事实、一半是过期营销**：Google 官方确实至今仍然建议 SSR 或预渲染，但给出的理由不是"Google 读不懂 JS"，而是"更快"和"并非所有漫游器执行 JS" [24]；实测数据显示 Google 对 JS 页面的整页渲染成功率接近 100%、渲染延迟中位数仅 10 秒 [26]。SSR 今天真实且不可替代的收益面已经**从 Google 迁移到了不执行 JS 的第二类爬虫**（社交/IM 链接预览、AI 抓取器），以及首屏与转化 [26][30][31][48]。

## Executive Summary

这份报告回答三个问题，并按用户要求把第三个问题写成**质疑**而不是复述。

**第一，"那么多人用"到底是多少人。** State of JavaScript 2025 中 React 使用率 83%，是所有前端框架里最高的一项，但同一年它也是负面情绪最集中的项目；Next.js 使用率 59%，负面情绪 17%，是全报告"引发评论最多"的条目 [1][3][15]。同一份调查的英文独立报道还补了一条常被省略的数字：**React 使用率 83% 的同时有 16% 的受访者表达不满**，Cloudflare Workers 的使用率一年之内从 1% 跳到 12% [15]。Stack Overflow 2025 的口径下 React 约 44.7%、Vue 17.6%（问卷基数与抽样人群不同，两套数字不可混用）[4][20]。npm 侧的量级差异更直白：React 周下载约 9,600 万，Vue 约 900 万，差近十倍 [21]——但这组数本身要小心：同一时间窗内不同来源给出的 React 周下载量从 2,500 万到 9,600 万不等，PkgPulse 自己也注明"这个 10 倍差距有一部分是虚高——React 是成千上万个包与元框架的间接依赖" [21][22]。与此同时，满意度信号在漏水：Next.js 的用户保留率从 2022 年的 89% 掉到 2023 年的 75% [11]，Svelte/Astro/Solid 的"愿意再用"比例均高于 React [23]。

**第二，为什么是它们。** 五条结构性成因，按解释力排序：① **先发 + 抽象契合**（2013 年前后唯一同时给出 vdom+JSX+单向数据流并被大厂背书的方案）；② **"局部解"策略带来的生态飞轮**（只解决渲染层，其余交给 npm，于是可选组件、教程、问答、招聘 JD 全部自我强化）[14][23]；③ **跨端复用**（React Native 让"一次学习多端交付"成为管理层的采购理由，并被写进 React 官方推荐位）[13]；④ **官方文档把入口指向框架，而 Next.js 是 RSC 最完整的实现**——这不是第三方传言，是 react.dev 的原话 [13]；⑤ **AI 的训练数据反哺**：GPT-5 提示指南推荐三个框架，是 Next.js(TS)、React、HTML；OpenAI 研究员明确说"按流行度和普遍性选的，没有和框架团队合作"，这恰恰构成一个无意图但自我强化的回路 [44][22]。

**第三，SSR/SEO 这个卖点，成立在哪里、失真在哪里。** 成立的硬内核只有一条：**Google 官方文档至今仍然写着"依然建议您采取服务器端渲染或预渲染"**，理由两条——用户和抓取工具更快看到内容、**并非所有漫游器都能运行 JavaScript** [24]。这条建议的存在本身就是 SSR 价值的最强背书。失真的部分同样有据：Google 不仅能执行 JS，而且是**通用渲染**（尝试渲染它抓到的所有 HTML 页面，不是 JS 页面才渲染），实测整页渲染成功率接近 100%，渲染延迟 25 分位 4 秒、中位 10 秒、99 分位约 18 小时——"排队几周"的老信念在主流站点上已不成立 [26][27]。真正的剩余风险被压缩成几个非常具体的工程条件：**初始 HTML 里带 `noindex` 的页面不会被渲染**（客户端再删掉无效）、非 200 状态码可能不进渲染器、`canonical` 不建议用 JS 设置、应用 Shell 模型下内容依赖 JS 才可见 [24][26]。而"不执行 JS 的爬虫"这一类，重心已从搜索引擎迁到 **Slack/WhatsApp/LinkedIn/Facebook 一类链接展开机器人**——Slack 官方原文说它"尽可能少地抓取页面内容（用 HTTP Range 头）来提取 meta 标签"，并且不遵守 robots.txt [30][49]；把 `og:*` 用 `document.head.appendChild()` 注入对这类爬虫完全无效 [32]。而**同一种"不执行 JS"的行为模式正在 AI 抓取器上重现**：Vercel 与 MERJ 在 2024 年 12 月 17 日发布、分析了超过 5 亿次 GPTBot 抓取的研究结论是"目前没有一家主流 AI 爬虫渲染 JavaScript"（GPTBot、OAI-SearchBot、ChatGPT-User、ClaudeBot、PerplexityBot、Bytespider、Meta-ExternalAgent 全部为"未观测到执行"，Googlebot 与 Applebot 则为"是"）[25][33][60]。最后还有一层价值坍缩：AI Overviews 让"排名第一"不再等于"流量第一"，Ahrefs 测得有 AI 摘要时首位点击率下降 58%（同口径 2025 年 4 月是 -34.5%，一年内扩大近一倍）[45]，Pew 观测到有摘要时点击传统结果的比例是 8%，无摘要时 15% [48]。**结论：把 SSR/SEO 当"核心卖点"是 2016–2020 年的叙事惯性；2026 年它更准确的名称是"首屏性能 + 元数据可机读性"，其中后者的受众已从搜索引擎扩大到社交爬虫与 AI 抓取器。**

## 1. 现状基线：采用率的事实基础 [Confidence: High]

先把"很多人用"变成一个可核对的量。三套主流口径同时存在，而且彼此不可互换，这是多数讨论把水位讲糊的第一步。

**State of JavaScript（自选择样本，偏社区情绪）**：2025 年报告中 React 使用率约 83%，仍是第一名；Next.js 使用率 59%，正面 21%、负面 17%，是全部条目里"引发评论最多"的一项 [1][3]。前端框架的痛点榜给出了一个方向一致的信号：**排在第一位的痛点是 "React issues"（React 本身的问题），紧随其后的是"过度复杂"（Excessive complexity）与"性能"，第四是状态管理，第五是"选择过载"（Choice overload），版本变更与依赖问题分别在第六和第八** [1][3][15]。换句话说，社区抱怨的首要对象是**框架本身和它的复杂度**，而不是渲染模型；满意度均值约 3.7–3.8（满分 5），Solid 连续第五年保持最高满意度 [1][3][15]。State of React 2025 的独立调查给出总体幸福感 3.6/5，96% 的受访者用它构建 Web 应用；在"对生态参与方的观感"这一题上，**对 Vercel 参与的负面评价（23% 负面 + 13% 非常负面 = 36%）超过了正面评价（19% + 6% = 25%）**，而被认为"新近宣布的 React 基金会"则获得压倒性正面（32% 正面 + 18% 非常正面）[9]。

**Stack Overflow（自选择样本，偏从业者）**：2025 年问卷中 JavaScript 使用率 66%、TypeScript 43.6%（一手抓取确认）[4]；框架项下 React 约 44.7%、Vue 17.6%、Svelte 7.2%，转引口径一致 [5][20]。

**npm / 网站技术普查（偏客观行为）**：React 周下载约 9,600 万，Vue 约 900 万，差近十倍；React 相关包约占 npm 生态份额 61%（Angular 28%、Vue 10%）；W3Techs 2026 年 4 月统计显示全球网站中 React 使用比例约 7.9%、Vue 0.9% [21]。同一套 W3Techs 数据显示，**全球有 1.9% 的网站由 Vercel 承载托管** [8]。

时间维度上，Next.js 的位置不是天然形成的。State of JS 2022 中它在渲染框架里排第一（48.6%），但彼时"兴趣度"已被 SvelteKit 和 Astro 追平；更关键的是**留存率结构**：Astro 与 SvelteKit 以 92% 的留存率高居榜首，Next.js 90%，而上一代的 Gatsby 从 2019 年的 90% 崩到 2022 年的 38%，同一年 React 自己的留存率也从 2019 年的 89% 降到 83% [12]。Gatsby 的塌陷是理解"Next.js 为什么是它"的关键反例——**元框架的更替可以是一夜之间的，且更替的驱动变量是默认渲染模型与官方文档推荐位，不是框架本身的功能数量**。一年后，Next.js 自己的留存率也从 89%（2022）降到 75%（2023）[11]。这个斜率比任何评论都更早地预警了 2025 年的负面情绪。

综合起来，"那么多人用"是事实，但它同时包含两个相反的信号：**绝对装机量仍在扩大，相对满意度在漏水**。pkgpulse 的解读值得作为方法记住：满意度到采用变化之间存在 2–4 年的滞后，且"62% 满意度 × 60% 市场份额"仍然是绝对数量上最多的满意开发者 [23]。这句话是 [Low] 置信（单一 Tier 3 来源的推断），但它正确描述了本报告反复看到的一个结构：**React/Next.js 的地位正在从"因为好用所以用"迁移到"因为已经在用所以继续用"。**

## 2. React 为什么赢：五条结构性成因 [Confidence: High]

### 2.1 抽象契合与先发背书

2013 年前后的前端战场里，React 是第一个把"虚拟 DOM + JSX + 单向数据流"打包成可用整体、并且由 Facebook 自家生产环境（News Feed、Ads Manager）验证过的方案。社区讨论长期把这一点列为首要成因：大厂背书降低了组织内的采购风险，vdom+JSX 提供了一个足够小、足够可组合的心智模型 [1][13]。这不是"最好的技术"论证，而是"最早足够好的技术"论证——后续所有优势都从这里派生。

### 2.2 "局部解"策略 → 生态飞轮

React 只解决"渲染"这一层，路由、状态、数据获取、样式、构建全部交给社区选型。这个决定在早期被批评为"不完整"，但它带来两个复利后果：第一，React 不与任何后端的框架决策冲突，因此可以嵌入任何存量系统（旧版 React 官方文档明确把"把 React 作为 `<script>` 加到已有页面"列为最简单的接入方式）[14]；第二，因为可插拔，围绕每个槽位都长出了一个竞争性生态（Redux/Zustand/Jotai、React Query/SWR、React Router/TanStack Router、styled-components/Tailwind……），生态的广度本身成了选型理由。npm 在 2017 年的 React 生态报告就记录了这一飞轮；到 2026 年，它的表述变成"引用 React 的 npm 包数量与问答量形成压倒性优势" [21][23]。

值得注意的反证是：**"局部解"带来的自由度正是今天认知过载的来源**。State of JS 2025 把"选择过多/过度复杂/版本变更"列为 React 的长期痛点 [1][11]，而 react.dev 之所以在 2023 年改口推荐框架，本质上就是官方承认"槽位自由"在规模化后变成了负资产 [13][14]。

### 2.3 跨端复用：把选型议题升维到管理层

React Native 让"一套思维交付 iOS/Android"成为可能，这使 React 的采购理由从技术优势变成**人力资产复用**。Expo 至今仍占据 react.dev 推荐位第三条，定位是"创建真正的原生 UI 的通用 Android/iOS/web 框架" [13]。这条推荐位的存在本身就是成因 2.3 的官方证据。

同时，跨端这条线也是当前最响的反方证据来源：Netflix 在 2017 年为了让未登录首页在 3G 下达标，**把客户端的 React 换成了原生 JavaScript**，JS 总量减少 200KB 以上、TTI 缩短超过 50%，而服务端仍继续使用 React 渲染 [34][36]。这段历史在 2024 年 10 月被一条浏览量 150 万的推文篡改成"Netflix 删除了 React"，而事实是原文标题里最关键的两个词 `client-side React.js` 被删掉了 [36]。Airbnb 于 2018 年撤出 React Native；**Shopify 则在 2026 年 9 月 10 日宣布移动应用全面回归 Swift/Kotlin，官方理由是"LLM 改变了我们 2020 年决策所依据的核心假设之一"**——"两套代码等于两倍人力"这个等式不再成立，于是"写一遍"的优势被 AI 削弱了 [53][54][55]。这三条合起来说明：React 的跨端红利从来不是永久性的，它随**相对成本函数**变化，而 AI 正在改变这个函数。

### 2.4 官方文档把新项目入口指向框架（决定性一击）

这是本报告中证据等级最高的一节，因为一手原文可核对。旧版 React 文档（legacy.reactjs.org）的推荐是分场景的："学习 React 或创建新的单页应用 → Create React App；**用 Node.js 构建服务端渲染的网站 → 试试 Next.js**；构建内容主导的静态网站 → 试试 Gatsby" [14]。新版 react.dev《Creating a React App》则改为一句无条件总则：**"If you want to build a new app or website with React, we recommend starting with a framework."**，并把 Next.js（App Router）列为第一个、也是唯一被描述为"充分利用 React 架构"的推荐项，同时明确写出 **"Next.js 的 App Router 是目前最完整的（RSC）实现"** [13]。

这次改口引发了两年的社区反弹（尤雨溪等人的批评），最终在 2025 年 2 月以妥协收场：React 团队采纳 Mark Erikson 的 PR 建议，保留"框架作为默认推荐"的同时**新增"从头开始构建 React 应用"一节**，推荐 Vite / Rsbuild / Parcel 作为构建工具、React Router / TanStack Router 作为路由、React Query / SWR / RTK Query 作为数据获取 [13][17]。

这条线索的意义在于：**"用 React 的人为什么用 Next.js"这个子问题，答案有一半写在 React 官方文档的第一屏上。** 但它同样重要地给出了 SSR 的第一处祛魅——react.dev 在同一页专门加了一个 Note：**"全栈框架并不要求服务器"**，所有推荐框架都支持 CSR/SPA/SSG，可以部署到 CDN 或静态托管，并且**可以按路由粒度**选择性开启 SSR [13]。官方叙事已从"要 SEO 所以要 SSR"迁移到"默认可以纯静态，需要时按路由加服务端"。

### 2.5 AI 训练数据构成的自我强化回路（新增变量）

The New Stack 对 2025 年的年度总结把这一点列为最大趋势：**LLM 倾向于默认输出 React 与 Next.js 代码，因为 React 主导前端，模型有海量 React 语料可训练** [44]。可核对的硬细节是：OpenAI 的 GPT-5 提示指南中推荐的三个框架是 Next.js(TypeScript)、React 和 HTML；作者直接问 OpenAI 研究员 Ishaan Singal 是否与 Next.js/React 团队有过合作以优化支持，回答是**"我们根据这些框架的流行度和普遍性选择了它们，但没有就 GPT-5 与 Next.js 或 React 团队直接合作"** [44]。这个回答排除了"商业共谋"的解释，却指向更结构性的一种：**没有人在策划，但默认值已经形成。**

中文社区给出的机制补充更细，但均为 Tier 3：JSX 把结构/逻辑/样式收在单文件里，对模型的解析与生成更友好，"能跑起来的代码"在 RLHF 阶段拿高分，于是 React 路径被反复强化；另一层是训练语料的地理偏差——Vue 在中文互联网极流行，但中文语料在大模型训练集里权重远低于英文 [22]。可量化的分区证据值得记住：全球 JavaScript 框架份额中 React 约 33%、Vue 约 6%；而把范围缩到中国 `.cn` 域名，**Vue 约 30%、React 只有 12%** [22]。同一条中文报道还指出，把视角切回中国市场，Vue 的份额反转说明 React 的"默认地位"是**语言圈层现象，不是全球常数** [20][22]。

State of React 2025 顺带量化了这条回路的入口效应：开发者的学习途径中"文档"占 84%，而**"AI 工具（ChatGPT、Claude 等）"已占 54%，同比上升 2 位，排在自学（78%）之后** [9]。学习入口本身正在被 AI 中介化。

## 3. Next.js 为什么成为默认：工程叙事与商业机器 [Confidence: High]

### 3.1 官方叙事：它把自己定义成"React 的那一层"

nextjs.org 首页的自我描述值得逐字看：**"The React framework for the web. Next.js 用于构建全栈 Web 应用：你为 UI 写 React 组件，Next.js 提供围绕它们的路由、渲染、数据获取、缓存和构建工具。由 Vercel 维护。"** 最新稳定版 16.4.3，MIT 许可 [5]。注意这五件事里 **SSR 根本没有被单列为卖点**，它被收纳在"渲染（rendering）"这个更中性的词下面。这是官方口径与营销口径的第一处差异。

工程能力位上，Next.js 提供的确实是一整套 SEO 所需的机读性基础设施：`generateMetadata` / Metadata API 在服务端输出 `<title>`、`description`、`openGraph` 字段，`next/og` 在服务端用 Satori 把 JSX 渲染成 SVG 再由 sharp 栅格化为 PNG 以生成社交分享图，内置 `sitemap` / `robots` 约定文件、`next/image` 图片优化、App Router 默认静态渲染以及 ISR 增量再生 [5][51][32]。这些能力不是虚构的，它们是卖点得以成立的物质基础。

历史事实层面（Wikipedia 汇编，Tier 2）：Next.js 于 **2016 年 10 月 25 日**开源，作者是后来 Vercel 的 CEO Guillermo Rauch，现任主维护者是 Tim Neutkens；截至 2024 年 10 月，Walmart、Apple、Nike、Netflix、TikTok、Uber、Lyft、Starbucks、Spotify 等站点在使用它；**Google 在 2019 年向该项目贡献了 43 个 PR** [7]。最后这一条是"SSR/SEO 卖点"最容易被忽略的历史支点：**搜索引擎厂商自己曾是这个 SSR 框架的贡献者。** Next.js 13 发布文给出的量级是：周 npm 下载超 300 万、GitHub 星数约 9.4 万、贡献者 2,400+，并说明 React 底层研究有 Google Chrome Aurora 团队参与 [6]。

### 3.2 商业机器：开源引流 + 平台变现

Vercel 2015 年创立（原名 ZEIT），2020 年 4 月改名；融资节奏是 2020 年 $21M A 轮 → 2021 年 $102M → 2024 年 5 月 $250M（估值 $3.25B）→ **2025 年 9 月 F 轮 $300M，估值 $9.3B**，员工约 550 人 [8]。State of JS 2025 的托管服务榜上，**Vercel 是第二大托管服务（44%），仅次于 AWS（48%）**，而 AWS 同时也是 Vercel 底层的承载方 [3][8]。Vercel 的产品线（v0、AI SDK）把框架与 AI 开发工作流绑在同一账号下 [8]。同一份 Wikipedia 条目还记录了两个容易被忽略的收购动作：**2025 年 7 月 NuxtLabs（Vue 元框架 Nuxt 的公司）并入 Vercel**，以及 Better Auth、Tremor 等团队的加入 [8]——这条线索在 §7 会成为"锁定担忧"的直接证据之一。

框架与厂商的这种耦合，在社区里被明确表达为不满。State of JS 2025 的原始评论里，一条是"我在生产环境写了快 6 年 Next.js……工程很棒，但 **Next 的复杂度已经高得离谱**"，另一条是"**因为 Vercel 中心化的程度，我不会再用了**" [3]。State of React 2025 的量化结果与之一致（对 Vercel 参与负面 36% > 正面 25%）[9]。同时，社区里"Vercel 实际上已经接管了 React"是常见论断（Reddit 上流传最广的一条帖子里，作者把这件事类比成 2015 年 Joyent 与 io.js 的分叉前夜）[69]，而 Mark Erikson 的反驳指向因果方向：**Meta 本身不需要 RSC，它需要的是愿意投入实现资源的外部赞助者**——不是 Vercel 夺取了 React，而是 React 的能力路线图需要有人付钱实现 [13]。2025 年 10 月 Meta 宣布把 React 移交 Linux 基金会（React 基金会），正是对这一担忧的制度化回应 [9][8][18]。核心团队的人员分布（约 21 人中 14 人来自 Meta、5 人来自 Vercel、2 人独立）说明这是一个**双雇主共担的结构**，不是单厂商私有物 [13]。

### 3.3 部署可移植性：从"私有构建产物"到 Adapter API（本轮最重要的事实更新）

这是本次调研中变化最快、也最容易被过时叙事污染的一节，值得详细记录，因为它是"厂商锁定"这个批评的直接答案。

一年前（2025 年 5 月），Netlify 公开列出了它在支持 Next.js 时遇到的六类现实问题，其中第一条是：**Vercel 早在 2022 年就为框架提供了 Build Output API，但 Next.js 本身不遵循它、也没有适配器机制；Next.js 构建使用的是一种私有的、几乎没有文档记录的格式，随时可能变化**。后果是 Netlify、Cloudflare、AWS Amplify、SST、Google Firebase App Hosting、Azure Static Web Apps 都必须在构建后从磁盘读取 Vercel 定制的未文档化输出、转换成自家格式再写回磁盘 [41]。

2026 年 3 月这条链闭合了。**Next.js 官方在 3 月 25 日宣布 16.2 引入稳定的 Adapter API**，与 OpenNext、Netlify、Cloudflare、AWS Amplify、Google Cloud 共同设计；构建时 Next.js 现在产出一份**类型化、版本化的应用描述**（路由、预渲染、静态资源、运行时目标、依赖、缓存规则、路由决策），适配器消费它并映射到自家基础设施；适配器只需实现 `modifyConfig` 与 `onBuildComplete` 两个钩子，破坏性变更要求 Next.js 主版本号提升；**"成为 verified adapter"的条件是开源 + 通过完整测试套件，而 Vercel 自己的适配器也走同一份公开契约、没有私有钩子、并且是开源的** [38][40]。官方还承认了关键的一句：**"Each capability and how they interact with one another was never formally documented."**（这些能力彼此如何交互从未被正式记录过）[38]。Netlify 工程师 Philippe Serhal 的总结是：他们整理问题清单时发现，**90% 的问题共同点就是"缺少一个有文档的、稳定的配置与读取构建产物的机制"** [37][38]。Netlify 侧的表述更直白：**"Until now, Next.js builds on Vercel had been powered by undocumented code paths in Next.js and closed source on Vercel."** [37]

但**不能把"契约公开"读成"锁定问题已解决"**，两处一手证据划出了边界。第一，Next.js 官方自己的部署文档现在仍写着：Vercel 与 Bun 适配器已就位，而 **"Cloudflare 和 Netlify 正在开发基于 Adapter API 的 verified adapter"**，且未通过 Next.js 团队验证的适配器"功能支持与兼容性可能有所不同" [39]。第二，Cloudflare 给出了一个更强硬的行动（**博客首发于 2026 年 2 月，vinext 1.0 在 9 月底落地**）：**即便有了适配器 API，构建过程仍然依赖高度定制化的 Turbopack 工具链，而适配器只覆盖构建与部署两个环节；开发阶段 `next dev` 完全跑在 Node.js 里，无法接入其他运行时；如果用到平台特定 API（Durable Objects、KV、AI Bindings），开发环境根本测不了这些代码。** Cloudflare 的应对不是适配，而是**用 Vite 把 Next.js 的 API 重新实现了一遍**（`vinext`：路由、SSR、RSC、Server Actions、缓存、中间件全部以 Vite 插件形式重写，脚本里把 `next` 换成 `vinext` 即可，现有 `app/`、`pages/`、`next.config.js` 不用改），并说"我们原本也不认为这能成功" [42]。值得记下这项工作的量级与成果：由**一名工程师带 AI 在一周内重建**，消耗约 **1,100 美元 token**，实现过程由**约 8,000 个 Next.js 官方测试驱动**，结果是**构建最高快 4 倍、客户端包小 57%** [42]。他们对 OpenNext 的复盘同样直白："OpenNext 不得不对 Next.js 的构建输出做逆向工程……变成一场打地鼠游戏" [42]。

这一条是本报告里对"Next.js 是可移植的标准答案"最有杀伤力的反驳：**同一时间，框架方在公告"契约已开放"，而另一家巨头判断"开放得还不够，重写更便宜"。** 两者都是 2026 年的一手事实，报告把它们并列而非取舍。

## 4. SSR 与 SEO：原理、Google 渲染管线，以及"核心卖点"说法的由来 [Confidence: High]

### 4.1 两个术语的精确定义

**SSR（Server-Side Rendering，服务器端渲染）**：浏览器收到的第一个 HTTP 响应里，HTML 已经包含渲染好的内容，而不只是一个空壳 + 一段 JS。与之相对的是 **CSR（客户端渲染）**——服务端返回"应用 Shell"（app shell），内容要等浏览器执行 JavaScript 之后才出现。在它们之间还有 **SSG（构建时预渲染成静态 HTML）**、**ISR（增量静态再生，带过期时间的 SSG + 按需重validate）**，以及 Next.js App Router 引入的 **RSC（React Server Components，组件级决定在服务端还是浏览器运行）**与**流式 SSR**（`renderToPipeableStream` 让 HTML 分块到达，而不是等整页拼好）[5][13][29]。

SEO 侧的关键概念也一并对齐：**SEO（搜索引擎优化）**在这一节里具体落到"机器能否读到我的标题、描述、正文和结构化数据"。Google 的处理被官方分成三个阶段：**抓取（crawling）→ 呈现（rendering）→ 编入索引（indexing）** [24]。所谓"两波索引"就藏在这里：第一波用原始 HTML 建索引，第二波用渲染后的 DOM 更新它。围绕这条管线的一组机制决定了 SSR 的价值边界：`rel="canonical"`（规范网址）、`noindex`（禁止索引）、soft 404、History API 与片段路由、资源缓存与内容指纹 [24]。

### 4.2 卖点为什么成立：Google 官方至今仍在建议 SSR

最硬的一条证据不是任何博客，而是 Google 搜索文档的原文。《了解 JavaScript SEO 基础知识》在描述完渲染队列后紧接着写：

> "网页在此队列中的存在时长可能会是几秒钟，但也可能会是更长时间。一旦 Google 的资源允许，无头 Chromium 便会渲染相应网页并执行 JavaScript……**请注意，依然建议您采取服务器端渲染或预渲染，因为：(1) 它可让用户和抓取工具更快速地看到您的网站内容；(2) 并非所有漫游器都能运行 JavaScript。**" [24]

这段声明里有三层信息必须分开读。**第一层是结论**：官方推荐仍然成立，所以"SSR 有利于 SEO"不是谣言。第二层是理由的**措辞**：官方没有说"Google 读不到 JS"，而说"更快"和"别的漫游器不执行 JS"——这两条理由里没有一条支持"CSR 会被 Google 惩罚"这种民间表述。第三层是**它把 SSR 的合法性部分寄托在非 Google 爬虫上**，这与 4.4 节的社交/AI 爬虫证据链完全吻合。换句话说，Google 自己已经把这条论证的重心挪开了。

同一份文档还给出了若干只有服务端渲染能天然满足的细节：Googlebot 会把所有 **200 状态码**页面加入渲染队列，**除非 robots meta 标记或标头告知不要索引**；被 robots.txt 屏蔽的文件 Google 不会渲染其 JS；对 `canonical`，官方明确"可以用 JS 注入，**但我们不建议这样做**"，并给出避免 soft 404 的两种策略（JS 重定向到服务端返回 404 的网址，或用 JS 加 `noindex`）；要求单页应用用 History API 而不是片段做路由，否则 Googlebot 无法可靠解析；Web Rendering Service 可能**忽略 HTTP `Cache-Control` 标头**，因此需要内容指纹文件名；shadow DOM 与 light DOM 会被扁平化，"如果内容在渲染后的 HTML 里不可见，Google 就无法将其编入索引" [24]。对大型站点还有一层约束：Google 只渲染被抓取且未被屏蔽的 URL，而渲染后的 HTML 要重新解析链接、回灌抓取队列，这条链在超大规模站上会显著放大调度成本 [24]。

### 4.3 卖点在哪里失真：Google 早就通用渲染，而且很快

**"Google 无法渲染 JavaScript"这句话已经死了。** Google 的文档说明它使用常青 Chromium；实测研究进一步量化了"能渲染"到什么程度。Vercel 与 SEO/数据工程咨询公司 MERJ 在 2024 年 7 月 31 日发布研究，方法是在 `nextjs.org`（辅以 `monogram.io`、`basement.io`）上部署自定义 Edge Middleware 拦截搜索引擎机器人请求，并在给机器人的 HTML 响应里注入一个轻量 JS 库，页面渲染完成时向外部信标服务器回报 URL、请求 ID 与时间戳，再用服务器访问日志与信标配对——从而**第一次把"抓取到渲染"的时差变成可测量数据**。样本为 2024 年 4 月 1 日至 30 日的 10 万次以上 Googlebot 抓取、37,000 组成功配对的渲染记录 [26][27]。

四条"旧信念"被逐条推翻 [26]：

- **误区一"Google 渲染不了 JS"**：排除状态码错误与不可索引页面后，**100% 的 HTML 页面完成了整页渲染**，包括复杂 JS 交互页面；通过 API 异步加载的内容全部成功索引；Next.js 这个 React 框架被完整渲染；RSC 流式传输的内容也完整渲染，说明**流式输出不损害 SEO**；而且 Google 尝试渲染它抓到的**几乎所有** HTML 页面，不是只挑 JS 重的页面。
- **误区二"Google 区别对待 JS 页面"**：不存在针对 JS 的特殊流程；所有 200 页面一律渲染，304 用原始 200 内容渲染，其他 3xx/4xx/5xx **不渲染**；JS 复杂度与渲染成功率、与渲染延迟在 nextjs.org 的量级上**没有相关性**。
- **误区三"渲染队列严重影响 SEO"**：延迟分布为 **25 分位 4 秒、中位 10 秒、75 分位 26 秒、90 分位约 3 小时、95 分位约 6 小时、99 分位约 18 小时**。长尾确实存在，但"排队几周"不是常态。带 query string 的 URL 明显更慢（无 query 的 75 分位 22 秒，有 query 的 75 分位 31 分钟、90 分位约 8.5 小时）；`?ref=` 这类不影响内容的参数尤其如此。
- **误区四"JS 重的站点发现更慢"**：有**更新及时的 `sitemap.xml` 可以显著消除、甚至完全消除发现时差**。

这里必须做利益相关披露：**这是 Vercel 的博客 + Vercel 付费委托的咨询公司的研究，样本主体是 Vercel 自家的 `nextjs.org`**——一个由 Next.js 团队用 Next.js 构建、SEO 权重极高、被抓取频率极高的站点。结论在"高权重文档站"上成立，不能直接外推到一个新建的低权重站点（该研究自己在 Tier 3 转述语境中被大量这样误用 [27][41]）。即便如此，它与 Google 官方文档没有一处冲突，且给出了官方文档给不了的东西：分布数字。**这两条来源相互独立且方向一致，是本次调研中置信度最高的一组证据。**

MERJ 研究里还藏着一个被广泛忽略、但工程后果极其具体的陷阱，值得单独抄出来：

> "Pages with `noindex` meta tags **in the initial HTML response** were not rendered, regardless of JS content. **Client-side removal of `noindex` tags is not effective** for SEO purposes." [26]

这一句是 SSR 价值最扎实的现代理由之一：**如果你的初始 HTML 里带了 `noindex`（常见于鉴权页、维护模式、灰度页），Google 连渲染都不会做，你在客户端把它删掉毫无用处。** 这类问题的唯一解法就在服务端首包，不是任何前端优化。Google 在另一份专门讨论 `dynamic rendering` 的文档里把选型口径写得更直接：**它不推荐 dynamic rendering（即按需给爬虫返回服务端渲染结果），而是建议改用 server-side rendering、static rendering 或 hydration 三者之一** [70]。同一份文档与另一方向上对非 200 状态码的澄清一起构成官方口径 [24][26][70]。

### 4.4 为什么"核心卖点"这个说法形成了：它曾经是字面意义上的真

"SSR/SEO 是核心卖点"不是营销凭空造的，它有三段真实历史支撑。第一段是 2009–2015 年 Google 的 **AJAX crawling scheme**——那时搜索引擎确实基本看不见 JS 生成的内容，网站必须为爬虫准备一套单独的 HTML 快照（`_escaped_fragment_`），Google 官方文档今天仍把这段列为"权宜之计"并早已弃用 [26][24]。第二段是 2015–2018 年的早期渲染，用的是**老版本**无头 Chrome，处理现代 JS 特性有真实局限 [26]。第三段是最要紧的：**Next.js 诞生即解决这个痛点**。旧版 React 官方文档的分场景推荐里，"要 SSR 就用 Next.js"是明文写的：**"如果你是在用 Node.js 构建服务端渲染的网站，试试 Next.js"**，同页还把 Gatsby 指定给"内容主导的静态网站" [14]。这份推荐位维持了约六年，它把"服务端渲染"从一件"需要自己搭一套的工程"变成"换一个脚手架就能拿到的默认值"——对 2016–2022 年间大多数既要 SEO 又要 React 的团队，那是当时成本最低的解。卖点就是这么形成的，不是被造出来的。

卖点形成之后，还有一层机制让它继续自我复制：Next.js 的官方文档同时输出 `llms.txt` 索引供 AI 抓取 [5]，而 LLM 的默认输出又回到 React/Next.js [44]。**卖点的传播链和产品的推荐链是同一条链。**

但还有一处更微妙的闭环，它反而削弱了这个卖点：Google 在近年陆续撤掉了"JS 页面需要特殊处理"的告警口径，工程师在官方播客里反复确认会对**所有**网页做渲染，包括重度依赖 JS 的 [63]。这个技术上的好意客观上把 CSR 的可行性推高了，于是"SSR 才能做 SEO"的差异化被抹平——卖点剩下的部分只能往别的受体身上迁（见 5.2 与 6.1）。

## 5. 质疑前提：把"SSR/SEO 是核心卖点"拆开验货 [Confidence: High]

用户的原始假设是"SSR/SEO 被称为 Next.js 的核心卖点"。经全篇证据检验，可以给出一个分层的裁决。

### 5.1 裁决一：CSR 也能排名——这句话成立，且官方亲自背书

Google 能通用渲染、成功率接近 100%、中位延迟 10 秒 [24][26]；react.dev 专门声明框架可以纯静态部署到 CDN、不需要服务器 [13]。因此"不上 SSR 就做不了 SEO"是**错的**。但要注意这句话的边界，Vue 官方文档给出了那个常被省略的限定语：**Google 和 Bing 能很好地索引"同步"的 JavaScript 应用；如果你的应用以 loading 动画开场、然后再通过 Ajax 拉取内容，爬虫并不会等待** [28]。这句限定与 MERJ 的实测并不矛盾——MERJ 测的是"最终能不能渲染出来"（能，且异步 API 内容全部索引成功），Vue 说的是"要多久、以及首包里有没有东西"。两者合起来才是完整答案：**CSR 能被索引，但你放弃了首包，把内容的可见性押在渲染队列和第二类爬虫的行为上。**

### 5.2 裁决二：SSR 的真实收益已经换了受体

第一类受体是**不执行 JavaScript 的社交与 IM 爬虫**。这一类的证据几乎全部是一手协议文本：Slack 官方 `api.slack.com/robots` 写着 `Slackbot-LinkExpanding` "**尽可能少地抓取页面内容（使用 HTTP Range 头）来提取 meta 标签**，具体寻找 oEmbed 与 Twitter Card / Open Graph 标签"，响应在全服务缓存约 30 分钟，并且"**我们目前不支持 robots.txt 文件**" [30]。Vercel 的 Bot Management 文档独立记录了同一套机制（按 Range 取部分内容、缓存后复用），这是本报告为该事实找到的**第二个互不隶属的来源** [49]。工程后果是可复现的：中文前端社区的复现总结是"**社交平台爬虫（如 `facebookexternalhit/1.1`、`Twitterbot`）只解析 HTML 初始响应的内容，不执行 JS，也不渲染客户端框架补丁**"，因此 `og:*` 必须写在初始 HTML 的 `<head>` 里，`og:image` 必须是能返回 200 的绝对 HTTPS 地址并显式声明宽高（推荐 1200×630），否则会被降级成占位图 [32]。**在 `useEffect` / `mounted` 里用 `document.head.appendChild()` 插入 `<meta property="og:*">`，对这类爬虫等于没写** [31][32]。这一类受体不会因为 Google 升级渲染器而消失，因为它们的工程目标是**低成本、低延迟、可规模化**，不是把 SPA 渲染出来 [30][49]。

第二类受体是 **AI 抓取器**。这一类比 2024 年时已经证据充分得多：**Vercel 与 MERJ 于 2024 年 12 月 17 日发布的研究（分析超过 5 亿次 GPTBot 抓取）结论是"目前没有一家主流 AI 爬虫渲染 JavaScript"**，表中 GPTBot、OAI-SearchBot、ChatGPT-User、ClaudeBot、PerplexityBot、Bytespider、Meta-ExternalAgent 全部标为"未观测到执行"，而 Googlebot 与 Applebot 标为"是" [25][33]。一个关键细节是：这些爬虫**会下载 JS 文件但不执行它**——ChatGPT 系列在 11.50% 的请求里下载了 JS，Claude 系列在 23.84%，但仍不运行 [25]。机制层面的解释很朴素：**AI 抓取每天面对百亿级页面，一个 headless Chrome 实例的 CPU/内存开销是 curl 类的几百倍，对训练目的而言在商业上不划算** [60][31]。本节不在此展开，因为它与"AI 搜索对 SEO 本身的侵蚀"必须合并讨论，见 §6.1–§6.3。

第三类受体根本不是 SEO，而是**用户**：Google 官方给出的第一条理由是"让用户和抓取工具更快速地看到内容" [24]。web.dev 的经典文献把服务端方案的性能账写成了那句被引用最多的话——SSR 带来的是**"一个应用、两份代价（one app for the price of two）"的水合问题** [29]：服务端把 HTML 算好，浏览器还要下载 JS、再执行一遍来"接管"这段 DOM（hydration），期间页面**看起来能用但点不动**，形成所谓"可点击幻觉"。MERJ/Vercel 一侧引用的商业数字是 Deloitte 的"每节省 100ms 与转化率 +8% 相关" [26]（该引用出自 Vercel 博客转述，Tier 2 且利益相关，只作方向性参考）。

### 5.3 裁决三：SSR 自身是有代价的，而且代价不在"SEO 那一侧"

TTFB 会直接暴露服务端关键路径的耗时；水合会推高 TBT/INP；`renderToString` 是同步串行的，要变好需要流式；SSG 有更短 TTFB 与更好的 CDN 复用但数据会陈旧；ISR、partial hydration、RSC、Edge Rendering 是同一批问题的不同折中 [29][13][5]。这条链上最实用的现代解是 react.dev 也承认的粒度化：**按路由开 SSR，而不是全站开** [13]。

### 5.4 裁决四：为 SEO 而建的服务端能力，正在成为攻击面

这是本轮调研中一个"没人这样讲卖点"的发现，值得单独列。**先说清一句边界：下面每一条都标注了受体与部署形态，因为"Next.js 不安全"这种笼统说法是错的——准确的说法是"Next.js 那些为 SEO/社交可见性而建的服务端能力，在自托管形态下构成一个新的攻击面"。**

最典型的一条：Next.js 专门用于生成社交分享图的 `next/og` 模块（把 JSX 经 Satori 渲染成 SVG、再由 sharp 栅格化成 PNG，**OG 图片路由通常无需认证即可访问**）在 **2026 年 9 月 22–23 日**被披露为未授权远程代码执行漏洞 **CVE-2026-94545**。根因不在 Next.js 自己写的代码里，而在它依赖的 **Satori 对内联 SVG 的文本内容未做正确转义**（CWE-116）：攻击者构造的输入被注入任意 SVG/XML 标记后，交由 `sharp` 底层原生库（libvips、librsvg、libxml2）解析时触发内存破坏，最终以服务进程权限执行任意命令。奇安信 CERT 给出 **CVSS 3.1 评分 9.8、高危、POC 与 EXP 均已公开**，鹰图测绘到国内关联风险资产 385,701 个、全球 2,772,161 个；修复版 16.3.6 与 Satori 0.33.5；**只有跑在 Node.js 运行时且安装了 sharp 的部署受影响，改用 edge 运行时（沙箱化 resvg-wasm）或未装 sharp 的不受影响** [51][66]。

同一批被修掉的还有几条，**它们全部长在"服务端能力"这条枝上**，值得按受体分组看：

- **图片优化 API**：CVE-2026-96889（GHSA-2464-fhr4-w9xw，Critical 9.5）——`/_next/image` 经 sharp→libvips→**静态链入的 librsvg** 触发释放后使用（CWE-416，上游 RustSec-2026-0305 修在 librsvg 2.63.2），**无需认证、无需交互、默认配置即可触发**；拿到完整执行权还需 glibc Linux 与非 PIE 的 node 构建，其他情形降为 DoS。影响 10.0.0–15.5.27 与 16.0.1–16.4.0，修复版 15.5.28 / 16.4.1 并把 sharp 声明抬到 ≥ 0.35.5。**2026 年 10 月 14 日那次计划外更新一次修了三个问题，其中两个 Critical 都在图片与缓存路径上** [52][67]。
- **ISR 与增量缓存**：CVE-2026-75604（CVSS 9.0）——文件系统缓存路径**未对反斜杠转义**，在 Windows 上可路径穿越读出 Server Action 的 `encryptionKey`，再伪造绑定参数达成未授权 RCE；需同时使用 Pages Router 与 App Router 且未启用 Cache Components，修复版 15.5.24 / 16.3.3 [66]。
- **中间件与授权绕过**：更早的 **CVE-2025-29927（CVSS 9.1）** 因内部请求头 `x-middleware-subrequest`（本意是防递归请求造成无限循环）未校验是否来自可信环境，可被重放以整体跳过中间件、绕过授权 cookie 校验，载荷形如 `x-middleware-subrequest: middleware:middleware:middleware:middleware:middleware` [50][58]；2026 年还出现**针对 CVE-2026-44575 的修复未应用到 Turbopack 构建下的 `middleware.ts`** 而形成的新绕过（CVE-2026-45109）[65]。
- **SSRF 与 Server Actions**：经 WebSocket upgrade 请求的 SSRF（CVE-2026-44578，官方缓解建议是"不要把源站直接暴露给不受信任网络，并在 Nginx/Caddy/Apache 层阻断 WebSocket 升级请求"）、自定义 Node.js 服务器上 Server Actions 的出站重定向，以及 Edge 运行时**无限制的 ServerAction 载荷导致内存耗尽** [65][67]。

量级也能佐证风险面：一次 2026 年 8 月的计划外安全更新同时修了两个 Critical，而官方口径里 Next.js 的**周下载量已超过 4,500 万**；此后 Next.js **宣布启动月度安全更新计划**——这条是厂商侧正在收敛的证据，应当与上面的清单并列记录 [64][65]。

一个必须原样记录的重要细节：CVE-2025-29927 **仅影响使用 `next start` 与 `output: standalone` 的自托管部署，托管在 Vercel 和 Netlify 上、或以静态导出方式部署的应用不受影响** [50]。同一方向的第二例是 Isomer 团队披露的**未授权拒绝服务**：单个精心构造的请求即可打挂一个自托管的 Next.js 实例，而**只做限流不够，必须在反向代理层限制请求体**，修复版 15.5.5 / 16.0.0；披露方特别注明该漏洞**由一个 AI AppSec Agent 首先发现**，且同样不影响 Vercel 托管 [47]。这条事实同时给两派都泼了冷水：对"自托管更自由"的说法，它说明**Next.js 的复杂度风险在自托管方由你自己承担**；对"只有 Vercel 才安全"的说法，它只是说明厂商运维替你兜住了一层——而兜住它的正是那份"未文档化的代码路径" [37][41]。

还有一处细节，比任何单个 CVE 都更能说明问题的性质：**依赖扫描工具看不见这条风险**。有从业者实测记录，9 月 23 日当天 `npm audit` 并未把 16.3.5 标为受影响版本，GitHub 安全公告库当时也尚未收录该条公告，公共漏洞库里查不到记录——也就是说，靠自动化工具做版本核对的团队会拿到一个"干净"的结果；而 **Satori 是被编译进 Next.js 包里的，锁文件里看不到它，无法从依赖清单判断版本** [68]。再加上这类对外 OG 路由通常由市场或数字团队持有、更新节奏跟内容日历而不是补丁周期走，形成的是一个**结构性错位**：为 SEO/社交可见性而建的服务端能力，落在一个既不在前端工程师日常职责里、也不在依赖扫描视野内的位置上 [68][51]。

## 6. 新兴趋势：SSR 的价值面正在被重新定价 [Confidence: High]

> 本节全部为 2024 年 12 月之后（多数为 2025–2026 年）的一手事实，符合"趋势类证据 <18 个月"的时效要求；例外条目已单独标注。

### 6.1 最重要的反转：Google 把"AI 可见性"重新接回了 JavaScript SEO

这是本轮调研收尾时发现的最有价值的一条闭环，方向和很多人以为的正好相反。

Google 搜索中心在 **2026 年 5 月 15 日**发布了首份面向生成式 AI 搜索的官方指南《针对 Google 搜索中的生成式 AI 功能优化网站》（搜索关系主管 John Mueller 署名）[2]。它先做了一次**减法**，把市场上两岁的 AEO/GEO 术语体系剪掉一大截：明确写着 Google 搜索**不使用**也不受益于专为 AI 准备的机器可读文件——"针对大模型的 llms.txt 文件是不需要的"、不需要内容分块（chunking）、不需要为 AI 系统专门重写内容、schema.org 结构化数据也不是"GEO 专用"手段而是整体 SEO 的一部分；原文口径是"许多流行的'AI 搜索优化'技巧（创建新的机器可读文件、AI 文本文件、Markdown）都可以被忽略"[2]。对上一节提到过 Next.js 官方文档输出 `llms.txt` 这件事 [5]，这意味着：**它是一个生态信号，不是一个索引信号**——两者不该混为一谈。

紧接着它做了一次**加法**，而且加的是同一条旧要求。指南的"满足搜索技术要求"一节写着：一个页面要能在生成式 AI 功能中展示，**前提是它必须已被索引，并且有资格在 Google 搜索中带摘要展示**；而在技术清单里专门有一条：**"如果你使用 JavaScript，请务必遵循 JavaScript SEO 最佳实践"**，理由是"使用 JavaScript 框架的网站做 SEO 通常比其他网站更复杂"[2]。换句话说，Google 否认了"AI 需要一套新优化"，却把 AI 可见性**重新挂回了 §4.2 那份 JavaScript SEO 文档**——而那份文档推荐的手段正是服务端渲染或预渲染 [24]。叠加另一条机制事实：AI Overviews 与常规搜索**共用同一套索引与 Googlebot 抓取**（因此业内称"混合 AI 爬虫"）[16]，于是 2016 年的那句话在 2026 年以另一种形式复活了：**不是"Google 读不懂你的 JS"，而是"你的页面得先进索引，而进索引的技术门槛官方仍建议用 SSR/预渲染来满足"**。

### 6.2 真正的威胁不是渲染，是零点击：侵蚀的实测数字

如果只看"能不能被读到"，SSR 的故事到 6.1 就结束了；但真正改变决策公式的是"被读到之后还有没有点击"。四条独立测量方向一致：

- Ahrefs 的追踪显示，出现 AI 摘要时**排名第一结果的自然点击率下降约 58%**；同一口径在 2025 年 4 月是 **-34.5%**，即一年内侵蚀幅度接近翻倍 [45]。
- SparkToro 的发布商调研给出 **68.01% 的搜索为零点击**，且每 1,000 次搜索仅带来 **276 次**流向开放网络的访问 [46]。
- Pew Research Center 的实测数据：结果页带 AI 摘要时点击传统链接的比例为 **8%**，不带时为 **15%**；约四分之一的查询会展开摘要中的引用链接 [48]。
- ISB-CMU 的**随机对照实验**（这是该领域少见的因果设计而非相关性观察）测得自然点击下降 **38%**，且 **95% 的用户没有察觉**到自己看到了 AI 摘要 [19]。

中文圈的汇编还补了两个运营侧数字：Semrush 统计的 AI Overviews 触发率从 2024 年初的 6.49% 升到 2025 年中的 24.61%、随后回落到 15.69%（说明波动本身也是常态），Seer 的观察是"排名第一"与"实际拿到的量"正在解耦 [10]。SISTRIX 的数据更陡：2026 年 3 月谷歌排名第一的点击率已从 27% 跌到 11% [2]。

这组数字对"SSR/SEO 是核心卖点"这句话的影响是**釜底抽薪式的**：SSR 优化的是"能否被机器读到"，而行业焦虑已经转移到"被读到之后值不值得点"。也因此，Next.js 的价值叙事正在从 SEO 向**内容交付质量与首屏体验**迁移——这也是为什么 §3.1 里官方首页把 SSR 收进"渲染"而不单列 [5]。

### 6.3 AI 抓取器不执行 JS：SSR 需求在新受体上重现（含一条必须写出的矛盾）

这是本报告与用户原始假设相关度最高的一节。**Vercel 与 MERJ 在 2024 年 12 月 17 日发布《The rise of the AI crawler》**，基于对 nextjs.org 与 Vercel 网络数月监测、超过 **5 亿次** GPTBot 抓取的分析，结论是"目前没有一家主流 AI 爬虫渲染 JavaScript"：GPTBot、OAI-SearchBot、ChatGPT-User、ClaudeBot、PerplexityBot、Bytespider、Meta-ExternalAgent 全部为"未观测到执行"，Googlebot 与 Applebot 为"是"；并且这些爬虫**会下载 JS 但不执行**——ChatGPT 系列在 11.50% 的请求里下载了 JS，Claude 系列在 23.84% [25][33]。中文译介与社区复现把同一结论传播得很广 [62][60]。机制解释在 §5.2 已经给出：一个 headless Chrome 实例的开销是 curl 类的数百倍，对抓取/训练目的在商业上不划算 [60]。

同一份研究还给出了两个常被引用时丢失的细节：AI 爬虫的**请求规模**已达到同期 Googlebot 45 亿次抓取的约 20% [62]，且流量**高度地理集中**；同时 AI 爬虫的 404/重定向比例远高于 Googlebot（后者只有 8.22% 的请求撞上 404、1.49% 撞重定向），说明**它们的链接发现质量更差**，对站点的抓取预算消耗方式不同于搜索引擎 [25][62]。

**必须原样呈现的矛盾（这是发现，不是误差）**：其一，第三方统计口径与"全部不执行"不完全一致——有工具给出"约 69% 的 AI 爬虫不能执行 JS"的分层结论，意味着少数已能执行 [25][59]。其二，2026 年的现场分享记录了**部分中国系模型（DeepSeek、Qwen、Kimi、Mistral 等）会渲染 JavaScript**，与西方主流抓取器的行为分叉 [59]。其三，Google 自家的 Gemini 走的是 Googlebot 基础设施，因此**具备完整 JS 渲染能力** [25][16]。三条合起来的正确表述不是"AI 爬虫不执行 JS"，而是：**"执行 JS 与否按抓取器逐个不同、且正在快速变化，因此把这个变量交给你的首包 HTML（SSR）是唯一能同时覆盖两者的做法"**。

还有一层不确定性要标出来：即使抓取器会读，**读到的东西也未必被诚实转述**。对多轮实测的社区总结指出，大模型会在没有实际访问页面的情况下**声称"读过"某 URL 并编造内容**，AI 引用链的可核验性明显低于搜索排名 [61]。这类研究目前全部是 Tier 3（厂商或从业者自测），只能作方向性参考。

### 6.4 AI 同时放大 React 的默认位，也削弱跨端红利

两条相反的作用力在同期发生。放大侧：The New Stack 的年度总结把"LLM 默认输出 React/Next.js"列为 2025 年最重要趋势之一——模型有海量 React 语料，于是默认产出 React，于是语料更多；OpenAI 研究员 Ishaan Singal 对"是否与框架团队合作优化"的回答是**"我们根据这些框架的流行度和普遍性选择了它们，但没有就 GPT-5 与 Next.js 或 React 团队直接合作"**，同时他也承认 Vercel 在发布当天称 GPT-5 为"最好的前端 AI 模型"，这是一种"互惠但无人策划"的结构 [44]。第三方分析把这条回路量化得更具体：**AI 编码工具已经标准化在 React + shadcn/ui 之上，形成自我强化的采用循环** [9]。

削弱侧：§2.3 的跨端理由正在被同一股力量反转。**Shopify 在 2026 年 9 月 10 日宣布其移动应用全面回归 Swift/Kotlin 原生，官方理由是"LLM 改变了我们 2020 年决策所依据的核心假设之一"**——当"两套代码等于两倍人力"不再成立，"写一遍"的优势就被削掉了 [53][54][55]。同一年，React 自身的治理也在去厂商化：**React 基金会在 2025 年 10 月 7 日宣布、2026 年 2 月 24 日正式在 Linux 基金会下成立**，成员含 Amazon、Expo、Callstack、Microsoft、Software Mansion、Vercel [18][9]。这条对"Vercel 是不是在替自己卖托管而塑造 React 路线"的质疑（§3.2）是一个制度化回应，但它改变的是治理外观，不改变 §3.3 记录的构建契约依赖。

### 6.5 可移植性成为主战场：从"要不要 SSR"到"能不能离开 Vercel"

选型争论的焦点在过去 18 个月发生了位移。§3.3 记录的三步（Netlify 的六类问题清单 [41] → Next.js 16.2 稳定 Adapter API + 开放 9,000+ 端到端测试套件作为正式契约 [38] → Cloudflare 判定"开放得不够，重写更便宜"并放出 vinext 1.0 [42]）本身就说明：**厂商之间现在争的不是渲染模型，而是构建产物与运行时的归属权**。OpenNext 侧的中立表述可作为第三方口径："那个 API 现在在 Next.js 16.2 中稳定，意味着平台不再需要对构建输出做逆向工程"，同时"AWS、Cloudflare、Netlify 的新适配器仍在积极开发中"[40]；Next.js 官方部署文档至今也把 Cloudflare 与 Netlify 的 verified adapter 列为"正在开发"[39]。而 vinext 1.0 的发布文里有一句对"要不要 SSR"这个问题很有代表性的重新表述：**如果你的站点是 100% 预构建静态 HTML，用 vinext 收益不大——不如花 10 美元迁到为静态内容设计的 Astro** [42]。这是第一次有巨头在官方文档里把"用哪个框架"与"用哪种渲染模型"分开定价。

### 6.6 AI 已经进入漏洞发现与框架重写两端

§5.4 记录了 Isomer 披露的未授权 DoS **由一个 AI AppSec Agent 首先发现** [47]；§3.3 记录了 vinext 由**一名工程师带 AI 在一周、约 1,100 美元 token 内重建**、并由约 8,000 个官方测试驱动 [42]；Next.js 16.2 自己也把 AI 编码代理做成一等公民（`create-next-app` 自动生成 `AGENTS.md`、包内置对应版本的 Markdown 文档供代理本地调用、浏览器错误默认转发到终端）[44][65]。三件事合起来是一个新变量：**框架的演进速度与攻击面的发现速度同时被 AI 拉高**，这让"选一个框架用十年"的隐含假设更站不住——也正是 §7 的入口。

## 7. 批判性评估：什么时候不该用 Next.js [Confidence: High]

前五节解释了它为什么赢；这一节是必要的反面。**结论先行：Next.js 在 2026 年是一个"默认正确答案，但错得越来越贵"的选择。** 证据分七组。

**① 生态分裂是最早被实测到的成本。** 文档与教程默认 App Router，但生产迁移远未完成：App Router 在学习者中的采用率约 67%，在**生产**环境只有约 34% [43]。这个 30+ 个百分点的落差意味着一个具体后果——**新人带进来的心智模型与仓库里的实际形态不一致**，招聘与培训成本被隐性抬高。§2.2 的"局部解带来自由度"在这里变成了它的对立面：RSC/Server Actions/App Router/Pages Router 的"既要又要"让"槽位自由"变成了"版本不确定"。

**② 满意度信号在漏水，而复杂度是被点名最多的那一项。** State of JS 2025 的痛点榜第一位就是 "React issues"，第二/第三是过度复杂与性能 [1][3][15]；原始评论里两条最常被引用："我在生产环境写了快 6 年 Next.js……Next 的复杂度已经高得离谱"、"虽然我用 Next 的体验不错，但我很担心，因为 Vercel 正试图靠它赚钱"[3]。第三方对留存趋势的跟踪给出了更陡的斜率：Next.js 的正面感受从 68% 降到 55%，同时 Turbopack 的满意度显著低于 Vite（Vite 的负面约 1%，Webpack 约 37%）[56][3]。选型讨论里"framework fatigue（框架疲劳）"已经从吐槽变成一个被认真对待的成本项 [35]。

**③ 厂商耦合与锁定：三条一手证据，且都来自 2025–2026 年。** 第一，Netlify 指出**许多未文档化行为藏在一个名为 `minimalMode` 的私有开关之后**，Vercel 上的 Next.js 站点走的是自己的专属代码路径，"一些供应商甚至反向实现了这个未文档化模式"[41]；Netlify 在 Adapter API 稳定后进一步写明，"到目前为止 Vercel 上的 Next.js 构建是由 Next.js 里未文档化的代码路径 + Vercel 上的闭源代码驱动的"，并预期这些路径会在下一个大版本被删除 [37]。第二，Vercel 在 2025 年 7 月把**竞品公司的框架（NuxtLabs）**收进旗下 [8]——这是社区"锁定担忧"最直接的弹药，State of React 2025 的原始结论明确写着受访者负面观感的动机是"对锁定的担忧、被推动的不需要的功能、以及创始人有争议的政治立场"[9]。第三，开发期锁定：Cloudflare 指出适配器只覆盖构建与部署，**开发阶段 `next dev` 完全跑在 Node.js 里**，用到平台特定 API 时开发环境根本测不了 [42]。

**④ 复杂度风险在自托管方由你自己承担。** §5.4 的 CVE 清单在这里换成决策语言重说一遍：`x-middleware-subrequest` 绕过（CVE-2025-29927）**只影响 `next start` / `output: standalone` 的自托管** [50][58]；未授权 DoS 也只在自托管形态需要你在反代层限请求体 [47]；`next/og` 与 `/_next/image` 的两个 Critical 需要 Node 运行时 + sharp 才成立 [51][52][66]。这不是"别自托管"的论证（那会把风险换成厂商依赖），而是**"自托管 Next.js 时，你要接手的那部分运维知识量远超一个后端服务"**——包括缓存同步、再验证传播、图片处理链的原生依赖、以及一个 `npm audit` 看不见的编译进包依赖 [68][41]。

**⑤ "好招人"这条理由要打上折扣。** 岗位需求侧仍压倒性地偏好 React/Next.js，中文招聘平台的统计里 Next.js 相关岗位长期位居前端 JD 技术栈前列 [57]。但把它和 §1 的留存率斜率、②的满意度、①的版本分裂放在一起读，得到的是一句更准确的话：**你招得到人，但招来的人带来的默认假设（App Router、Vercel 部署、RSC 心智模型）可能与你的存量系统不匹配。** 这是"因为已经在用所以继续用"（§1 结尾）在人力侧的具体形态。

**⑥ 反方最强的论点，以及它薄弱的地方。** 社区里对 Next.js 最系统的批评（Reddit 上流传较广的那一条）是：Vercel 通过雇佣关键贡献者主导 React 方向，大力推广 SSR 与 RSC，**"我们正在用开发者的自由换取一个为销售托管服务而优化的生态系统"** [69][35]。**它的强处是与 §3.3 的一手证据完全咬合** [69]；它的弱处是被 Mark Erikson 的因果反驳削弱——Meta 并非不需要外部实现者，React 的能力路线图需要有人付钱把它做出来 [13]，而基金会与 Adapter API 是这条质疑的两个可核对的制度化回应 [18][38]。**诚实的裁决：这是一个"利益结构真实存在、但尚无证据表明被恶意使用"的局面**，因此它应当进风险登记（第 ⑦ 条），不应当被当作否决理由。

**⑦ 一张"何时不该用"的判断表。** 下面每一条都能在 §1–§6 找到证据支撑，不是偏好判断：

| 你的情形 | 建议 | 依据（编号对应本文） |
|---|---|---|
| 后台/控制台/内部工具，无公开 SEO 诉求 | 纯 CSR + Vite（或本类项目的后端模板）足够，**不要为此引入 SSR** | CSR 能被完整索引且延迟中位 10 秒 [24][26]；"to B 管理后台 → React 就够了，别过度工程化" [35] |
| 内容型站点、以静态为主、极少动态数据 | 考虑 Astro/静态导出，而非在 Next.js 里做全量 SSG | Cloudflare 官方明确表示 100% 预构建静态场景用 Next.js 兼容层收益不大 [42] |
| 必须被社交/IM 分享且首包必须带元数据 | 需要服务端（SSR 或构建时预渲染二选一，别用运行时注入 meta） | 社交爬虫不执行 JS、按 Range 只取头部 [30][49][32] |
| 团队无 Node 运维能力、又要求自托管 | 这是最差的组合，改选更简单的栈或接受托管 | 缓存/再验证/图片链的原生依赖需自建运维知识 [41][68][47] |
| 强合规/数据出域限制，禁用境外托管 | 可用，但必须把自托管安全面写进方案并跟月度安全更新 | CVE-2025-29927 等仅影响自托管；Next.js 已启动月度安全更新计划 [50][64][65] |
| 需要"离开某平台的能力"作为采购条件 | 先确认你的关键能力是否在 verified adapter 覆盖内 | 官方文档列 Cloudflare/Netlify 适配器"仍在开发"[39]；PPR/再验证仍需定制 CDN 基础设施 [37] |
| 靠自然搜索流量生存的内容业务 | SSR 不再是决定性变量，**内容与结构化数据质量才是**；技术侧只需满足 JS SEO 清单 | 官方否认 AI 专用通道但要求遵循 JS SEO 实践 [2]；零点击侵蚀 [45][46][48][19] |

## 9. 开放问题与局限 [Confidence: Medium]

以下问题在本次调研预算内无法定论，列出是为了避免被当作已解决：

1. **"AI 抓取器不执行 JS"的结论有效期。** 2024 年 12 月的一手研究说"全部不执行" [25]，2026 年的现场记录说部分模型会执行 [59]，另一工具给 69% 的分层值 [25][59]。这类数字的**半衰期按月计**，任何基于它的架构决策都应附带"重新验证方法"（最便宜的是用 `curl` 拉首包并数可读正文字符 [60]）。
2. **llms.txt 与 SSR 哪个更重要。** Google 口径是两者无关 [2]，而厂商侧仍把 llms.txt 当特性输出 [5]。真实影响面取决于非 Google 的 AI 入口（ChatGPT/Claude/Perplexity）是否读该文件，目前没有一手证据。
3. **零点击侵蚀能否归因到渲染方式。** §6.2 的四条测量全部关心"展示形式"，没有一条按"CSR vs SSR"分层。因此"SSR 能否缓解流量下降"在本报告中**故意不给结论**——它不在证据能力范围内。
4. **中国侧检索引擎的行为未取证。** 本报告证据体系以 Google 为中心，涉及百度/神马的抓取与渲染行为只见于 Tier 3 转述 [31][60]，未做一手实测。中文内容站的结论不能直接从本文推出。
5. **MERJ 两项研究的利益相关。** 样本主体是 Vercel 自家站点（`nextjs.org`），且 MERJ 是 Vercel 付费方 [25][26]。结论与 Google 官方文档无冲突，但**不宜外推到新建低权重站点**。
6. **招聘侧数据仅中文市场。** [57] 是 Tier 3 单一来源，只支撑"岗位需求偏好"的方向，不支撑绝对量。

## Methodology

**深度与流程**：用户选定 **deep**（目标 30–50 源、6000+ 字、必须含反方证据链）。实际执行 Phase 0（澄清）→ 1（范围）→ 2（多波检索）→ 3（三角验证）→ 3.1（引用核对）→ 3.5（大纲微调）→ 4（红队自评）→ 5（撰写）。

**与技能默认管线的偏差（必须声明）**：本环境**没有通用检索子代理**（可用子代理仅 Browser / CodeReview / ComputerUse，均不适用于网页检索），因此 Retrieval / Gap-Fill / Verification / Synthesis 四个角色**全部由主代理以分批并行 WebSearch + 全文核对等效承担**。影响：主代理工具调用预算被检索占用更多，而撰写轮次变多（本报告正文分多次编辑完成）。按技能的"graceful degradation"条款处理，不掩盖。

**源规模**：最终 **70 条**（deep 目标 30–50 的上侧），其中 Tier 1 一手/官方文档 22 条、Tier 2 可信机构媒体与研究报告 20 条、Tier 3 补充（含中文社区与厂商博客）28 条。检索波次：Wave 1（4 个主题域并行）+ Wave 2–3（gap-fill：零点击实测、Adapter API 时间线、CVE 根因、AI 抓取器行为）+ 本轮**参考文献 URL 逐条复核**（15 次 WebSearch）。
