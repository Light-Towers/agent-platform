# 完成证据格式（roadmap 阶段 0 #2 的落地件）

**版本：** V1
**状态：** Reference（规范，非施工图）
**定位：** 回答一个问题——**"你说做完了"这句话，要写成什么样才可核对**。
**来源判据：** `docs/plans/plan-production-delivery-roadmap-2026-10-09.md` §二 阶段0 #2 原文要求
「定证据规范：**代码版本、执行命令、通过/跳过/未跑数量、所需依赖**」，判据为「规范入库并**用于后续所有条目**」。
**适用范围：** 仓内一切"完成/达标/已验证/全绿"类陈述 —— CHANGELOG 条目、`docs/TODO.md` 状态列、
`docs/plans/plan-*.md` 的交付记录、runbook 的结论行、评审与面试引用。
**不适用：** 纯设计讨论与方案文档（它们的主语是"打算怎么做"，不欠读数）。

---

## 1. 五个必填字段（缺任何一个，那句话就降级为"待证"）

| # | 字段 | 写法的硬要求 | 反例（本仓真实踩过的形状） |
|---|---|---|---|
| 1 | **代码版本** | 写明读数绑定的 rev（`git rev-parse --short HEAD` 或 Pod 内 `GIT_REV`）。跨 rev 后**必须重跑**才算现值 | 手册里写着「Jaeger ✅」而现网为假 —— 漏的就是这条（`AGENTS.md` 观测硬规矩第 3 条） |
| 2 | **执行命令** | 原样可复制的命令（含 `-m`/`-k`/`--extra` 等选择性参数），不是"跑了测试" | 「本机实跑通过」无命令 ⇒ 无人能复现，等价于没跑 |
| 3 | **读数 + 分母** | `passed / skipped / deselected / failed` 各数 + 该数的**口径**（哪个 session、几路参数、是否含 skip） | 同一规则两个数差很大（A=CI 等价 vs B=`--isolated` 真实存量），不写口径就是两个都对 |
| 4 | **未跑与待环境** | 明确列出**没跑的部分**和原因（缺 PG / 缺集群 / 缺密钥 / 被权限层拦下），标「待环境」「待放行」，**不写"已验证"** | 把"本地可执行的那半"写成整项完成（roadmap §四 第 2 条规则专门封这个形状） |
| 5 | **所需依赖** | 该读数成立的前置：venv extras、环境变量、外部服务、内网可达性 | 缺 OTel SDK 的自动 skip 被当成失败 / 反过来把缺依赖的跳过当成通过 |

模板（直接抄）：

```markdown
**读数**（rev `<short-sha>`，`<完整命令>`）：`N passed / M skipped / K deselected`。
**口径**：<哪些 session / 是否含 -m 过滤 / 分母是什么>。
**未覆盖**：<没跑的部分 + 原因（待环境 / 待放行 / 待拍板）>。
**前置**：<extras / env vars / 外部服务>。
```

## 2. 三条禁令

1. **不许脱离 rev 引用通过数。** "2912 passed"单独出现即失效；必须能指回"哪棵树、什么状态"。
   中途改树得到的读数要写成「代码树 X + 中途未入库的 Y」，并说明靠什么排除污染（见 §4 例 2）。
2. **不许用整体性名词描述现场证据。** "全仓""全部""都"这类词，必须能当场展开成
   `目标 | 命令 | 读数 | 结论` 的四列；展开不出来就改成具体覆盖面（例："三处 pydantic-settings 模型，逐一列出"）。
3. **转述别人的结论必须标为转述。** 子 agent / 他人评审 / 外部工具的结论，默认是"它说了什么"，
   不是"事实是"；要变成分支账面，需自己复跑一次。

## 3. 判"完成"的三条强度分级（写的时候选档，别混用）

| 档 | 成立条件 | 允许的措辞 |
|---|---|---|
| **已验证** | 五字段齐 + 命令当场可复跑 + 结论绑定 rev | 「已验证（rev X，命令…，读数…）」 |
| **标准环境已验证** | 只在标准/本地环境成立，多实例或真库未跑 | 「代码面达成 / 标准环境已验证，多物理机待环境」——**不得**简称"达标" |
| **待环境 / 待放行 / 待拍板** | 缺口在外部条件或决策上 | 只登记，**不承诺日期**，不得写成进度 |

roadmap §四 第 2 条的规则是本表的一个特例：**环境不可达时只能写第二、三档**，且交付介绍里不得出现依赖该环境的对外承诺。

## 4. 新加的自动检查必须附「非空转反证」

任何新增门禁（lint 规则 / 契约用例 / 存在性检查）交付时，必须给一张变异表：**让规则在人为破坏处报红**。

| 变异 | 期望 |
|---|---|
| 删掉被保护的那个键/锚点/装配点 | 用例报红（正向判据击中） |
| 改其值 | 用例报红（等值判据击中） |
| 塞一个不该存在的项 | 用例报红（不悬空判据击中） |
| 改判据自身的前提（前缀、枚举口径等） | 守卫用例报红 |

三条执行纪律，都是本仓实踩：
- **先分清"红的原因"**：`rc=1`（断言击中）才是反证；`rc=4` / `ModuleNotFoundError` 是**环境或用法错**，
  它证明的是探针没跑起来，不是规则生效。反证脚本必须用与门禁相同的入口（本仓 = `uv run pytest`）。
- **变异要按字节回来**：改文件跑反证 ⇒ 先 `read_bytes()` 备份，事后原字节写回并打印 `byte-identical: True`，
  再 `git status` 确认只剩 intended 改动。
- **否定性结论要第二条检索通道**：一条 grep 空命中 ≠ 不存在（猜类名的 `Receipt.*Store` 造成过假阴性；
  改成"按结构事实扫重复定义"才定位到）。空输出、被 `.gitignore` 吞掉、`.pyc` 污染都算这一类。

## 5. 计数的两条口径规则

1. **分层配置的数必须逐层取。** 本仓有 6 份 ruff config、多份 pyproject；只看根配置会把嵌套包的存量读成 0。
2. **多面标准必须逐面各取一次证据。** 判据写成"A、B、C、D 都可追溯"时，整体读一遍必然高估——
   要逐问查**谁写它**（生产写入点），不是查**有没有这个字段/类**。载体在位而字段无人填，是"未接线"，不是"达标"。

## 7. 怎么检查一份证据合不合规

```bash
# 无 rev 的"通过数"陈述（近似扫描，命中不等于违规，逐条人判）
git grep -nE "[0-9]+ passed" -- 'docs/**/*.md' CHANGELOG.md | grep -vE "rev|[0-9a-f]{7,}|HEAD"
# 空口径的整体性名词
git grep -nE "全仓|全部通过|都验证过" -- 'docs/**/*.md' CHANGELOG.md
```
这两条**故意不做成 CI 门禁**：判据需要语义判断，机械报红只会训练人去措辞规避（AGENTS.md
「框架的约束应是减少犯错而非阻碍绕过」）。要硬约束的地方已经硬了 —— 见 `scripts/lint_architecture.py` 的 P 系列。
