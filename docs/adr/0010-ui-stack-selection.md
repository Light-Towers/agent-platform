## 1. 现状（先纠正一个容易说反的事实）

**"完全没有界面"这句话不准确**：仓内已有一处服务端渲染的**只读控制台**——

| 件 | 位置 | 规模/性质 |
|---|---|---|
| 路由 | `applications/agent_server/api/console_router.py` | 39 行 |
| 页面 | `applications/agent_server/static/console.html` | 343 行 |
| 测试 | `applications/agent_server/tests/test_console_router.py` | 在册（agent_server session 122 passed 内） |

同时：**全仓没有任何 JS 前端工具链入库**——`git ls-files` 对 `package.json` / `vite` / `tsconfig` / `*.jsx` / `*.tsx` / `*.vue`
**零命中**（本轮实测）。⇒ 真实的选择题不是"有没有界面"，而是**"要不要为界面引入一套前端工程与构建链"**。

## 2. 未决的是什么

| 选项 | 做法 | 代价 / 风险 |
|---|---|---|
| **A 扩现有只读控制台**（服务端渲染 + 原生 JS） | 在 `console.html` / `console_router.py` 上加"提问 → 执行 → 展示过程与结果 → 错误提示"的交互面 | ① 零新工具链、零新部署面（镜像已含该路由）；② 复杂交互（流式渲染、断线重连、状态回溯）全靠手写，代码会长在应用里；③ 与 #18 判据「不新增后端专用接口」天然相容 |
| **B 新建独立前端工程**（Vue3/React + 构建产物静态托管） | 起 `web/` 工程，走现有 HTTP/SSE 接口 | ① 引入 Node 工具链 + 构建步骤 + CI 面（本仓现为纯 Python uv workspace，`make ci` 无 JS 段）；② 部署清单要改（镜像多一层或另起静态服务）；③ 收益是可维护的交互复杂度与组件复用 |
| **C 混合：A 起步、把 B 作为重启后的演进** | 先用 A 打通一条完整业务链路并留证据，触发条件满足再迁 B | 需明确"什么时候必须转 B"，否则会变成永久 A（见 §4） |

判据侧的硬约束（不是我加的，是 roadmap #18 自己写的）：**「一条完整业务链路真跑通，留截图与日志；不新增后端专用接口」**
⇒ 无论选 A 或 B，都只能消费现有对外接口；若发现必须新增接口，那是**契约变更**，要另立方案并按「边界」规则先审计消费方。

## 3. 否决理由（已被证据关掉的判断）
- **「先做前端框架选型再说」**：本轮实测显示仓内没有任何 JS 工具链，选 B 等于同时引入**工具链 + CI 段 + 部署面**三件事，
  不是换一个 CSS 框架那么轻；在选 B 之前必须先回答"谁维护这套构建"。
- **「已有控制台 ⇒ #18 已满足」**：不成立。`console_router.py` 是**只读**性质，#18 要求的是可发起一条业务链路并展示过程，
  这条判据目前没有任何证据。⇒ 别把"有个页面"当成"有界面能力"。

## 4. 重启条件（选 A 时也必须认这几条）
1. 交互需求出现**流式渲染 + 会话回溯 + 多步过程可视化**三者叠加 ⇒ A 的手写成本超过 B 的引入成本，必须转 B。
2. 界面对象从"内部演示"变成"外部用户自助使用"（要登录态、可访问性、错误恢复） ⇒ 必须转 B。
3. 任一版本要在页面上做前端构建产物发布 ⇒ 必须先把 Node 工具链与 CI 段落进 `make ci` 的口径里（现在没有）。

## 7. 决策维度拆分（2026-11-06 追加；起因是一次答错对象，§1–§6 历史论述照旧不改写）

**触发源**：用户问「前端为什么不用一个 Pod 独立部署」。AI 把这个问题答成了「入口怎么才能常驻可访问」，并给出了 NodePort。事后定位：**这不是口误，是账面缺陷** —— 本文 §6 的状态行写着「已决」，而 §6 决策的只有下面第 ① 维；任何后来者（包括我自己）都会把「已决」读成「前端相关的事都定了」，于是第 ③ 维这个**从未被决策过的缺位**被冒充成了已决。

| 维度 | 它回答的问题 | 可选态 | 当前态 | 决策出处 |
|---|---|---|---|---|
| ① 工程独立性 | 前端是不是独立工程与独立构建链 | 无工程（扩只读控制台）／有工程（web/ + Vue3 + Vite） | **有工程** | 本文 §6（2026-10-29 拍板） |
| ② 构建期 Node | 运行镜像里要不要 Node 进程 | 只在 build 期／运行期也背 | **只在 build 期** | Dockerfile 阶段 1；实施件 §10.2 形态 A″ |
| ③ 部署单元独立性 | dist 由谁托管、是不是独立 Pod | 同镜像同 Pod／独立静态服务 Pod／独立 SSR Pod | **同镜像同 Pod** | ⚠ 原先**缺位**，本 §7.1 补齐 |
| ④ 可达性 | 用户从哪儿进来 | ClusterIP 加转发／NodePort／Ingress | **NodePort 30080** | deploy/k8s/20-agent-platform.yaml 的 Service 段 |

② 与 ③ 正交、③ 与 ④ 正交 —— 两对都是本文原表述里容易合流的地方。**在册同型先例**：实施件 §10.3 第 1 条已经拆过一次同一种病（「开源自部署多一个 Node 运行时面」把 Next 这个名字当成了成本来源，而实测 Khoj 是纯静态导出、运行时无 Node），手法相同：把混在一起的两个维度拆开，再各自重新决策。本 §7 是这套手法的第二次应用。

### 7.1 ③ 维的决策（本次补齐，不是新开判断）

**维持同 Pod 静态托管，不拆独立前端 Pod。** 三条依据全部指向在册实物：

1. 形态 A″ 有三个跨框架的生产先例（Open WebUI / RAGFlow / Khoj，实施件 §10.2 逐行实测），「运行时无 Node」已被证成，拆出去不省这一层；
2. 拆出去会**新引入**一个当前不存在的风险源：独立前端反代 SSE 必须显式关掉代理缓冲，否则流被攒到结束一次性吐出、症状伪装成「前端卡顿」（§10.2 形态 C 的在册纪律）；这一层风险现在不存在的依据是两面读数：清单面 deploy/k8s 全仓零 Ingress 资源（实施件 §10.2 实测），集群面 ingressclass 读到 No resources found（NodePort 那刀当场现取）；
3. 拆出去**改变不了 ④ 维的任何结论**：可达性由 Service 类型支配，与 dist 住在哪个容器无关。

⇒ 收益只剩「前端可独立发布与回滚」一项，在 3 节点单盘、无专职前端、单页无路由的现状下兑现不了。**这是决策而不是否决**：§7.3 任一条件命中即重启，届时须另立实施件（本表只登记维度与决策，不含实施方案）。

### 7.2 一处必须点名的假锚（本节的直接起因）

deploy/k8s/20-agent-platform.yaml 的 Service 段注释第 3) 条原写「拆独立前端 Pod 改变不了『可达性由 Service 类型支配』这件事（同一读数的推导见台账 §43）」。**前半句是 ③ 维的判断，却被写在 ④ 维的依据列表里**；括号里的锚还是假的：docs/operations/evidence/2026-10-30-web-visual-references/readings.md 的 §43 实际内容是 port-forward 断连取证、入口逐格字节、以及「待人拍 ①：用户可达三选一」，**不含任何关于拆分部署单元的推导**（本轮对该节全文检索，零命中）。

这与本文 §6 末那条「路径存在 ≠ 锚点存在」同族：**锚点存在 ≠ 锚点含所引之结论**，后者比前者隐蔽——路径检索能过、节号也能对，而结论不在里面，所以它只能靠人去读，除非上齿（见 §7.4）。

本族的**真实实例计数 = 三次**（上一版本行写的是「§6 末、实施件 §11.4、本 §7.2」—— 把 §11.4 算进来是虚报：核对后它讲的是「已入库文档指向仓内**不存在的路径**」，属路径缺失那一族，不是错锚那一族；引用别人的类比而不本身核对，就会把计数读涨）：

1. 本文 §6 末：原写「选型文档 §10」，而该文档最大编号到 §8 ⇒ **节号越界**（锚不存在）；
2. 本 §7.2：台账 §43 存在、路径也对，而**结论不在节内** ⇒ 最隐蔽的一型；
3. 本 §7 写作过程中自己新犯的一例：初稿将 SPA fallback 那条边界归给实施件 §9.2，实取小节边界后知道它在 §9.1（L241 对 L243）⇒ **同一刀里当场重犯同型错误**，它才是本 §7 「要末上齿、要末别写」这句真正的反证。

### 7.3 重启条件（③ 维，沿用 §4 「预先写下触发条件」的手法）

1. 出现需要独立发布节奏的诉求（同一后端版本要发多版 UI，或 UI 要灰度）⇒ §7.1 那条唯一收益第一次真实存在；
2. 页面从单页变多页，或需要 SPA history fallback ⇒ 突破实施件 §9.1 末尾的在册边界（原文写在 §9.1 托管方式一节内：不做 fallback、最小核心无前端路由、深链刷新 404 属已知边界）；
3. 引入 HTTP 反代层（Ingress 或 apisix）⇒ 无论拆不拆，SSE 路径的关闭代理缓冲都从「事后排查项」升为「开工前置项」。

### 7.4 本 §7 随带的两处账面动作

- **清单注释订正（同批执行）**：Service 段依据第 3) 条撤下「见台账 §43」这个假锚，并把该条从「④ 的依据」降格为「指向本文 §7.1 的交叉引用」。原则重申一句：**清单注释不是决策载体**，形态判断一律住 ADR —— 这次它住错了地方，读者（我）就照着错的地方被误导了。
- **候选齿（登记，本批不装）**：scripts/check_doc_sync.py 现在只校**路径存在性**，它拦不住 §7.2 这类「路径对、内容不含所引结论」。候选判据 = 引用某节时，被引节必须含引用行里的一个关键 token。按范围纪律本轮不加齿；复审触发条件：下一次再出现「假锚被当作依据」的实例时必上（本族已累计三例，逐例见 §7.2；其中第三例就发生在本 §7 的初稿里，而它靠人工核对小节边界才发现 —— 这正是该齿值得上的证据，也是它本批仍然不该被顺手装上的证据）。
