## 1. 结论先行

**C：一套语义缓存契约、一个实现——Valkey 同时服务生产与开发/测试，PG 语义缓存整体退役。** 先单节点 Valkey，容量或延迟触到阈值再演进集群。开发/测试同样连真实 Valkey，不保留 PG 适配器，也不允许任何可配置的第二种缓存后端。

三条硬边界：

1. **单一实现**：`agent-runtime` 只提供 `ValkeySemanticCache`；`CACHE_BACKEND` 只接受 `valkey` / `disabled`，出现 `pg` 或其他值在启动期 fail-fast。生产清单必须 `CACHE_BACKEND=valkey`。没有第二套实现，也没有第二套生产定义。
2. **无自动切换**：Valkey 不可用时缓存 fail-open（请求继续、按 miss 处理、健康态报 degraded），**不回退到 PG 或其他存储**。后端只由配置显式选择，不由故障选择；需要关缓存时用 `CACHE_ENABLED=false` 或 `CACHE_BACKEND=disabled`，这是可审计的动作。
3. **开发/测试也跑真 Valkey**：仓库提供与生产同镜像、同索引/TTL 语义的本地 Valkey；CI 用 `valkey/valkey-bundle:9.1.2` service；契约测试缺服务即红，不允许 skip 冒充通过，也不允许用 PG 或内存假实现替代。与缓存存储无关的调用方单测可以显式关闭缓存或注入测试替身，但替身不得成为运行时可配置的后端。

C 不是 C2：C2 是「Valkey 生产 + PG 开发/测试适配器」，用户已明确否掉 PG 这半边。C 也不是 A/B/D：A 保留两套生产定义；B 把 PG 升为唯一实现；D 是两套生产后端的长期过渡态。**C 只允许一套实现、一套契约测试、一套运行语义。**

本 ADR 只记录决策与施工边界，**落盘时未修改任何代码**；#134 在 Stage 1 之前保持暂停。

### 2.3 联邦轨的"能力"有多少是真的

> **时点声明（2026-10-26 补）**：本节是**改造前基线**（取证时点 = 本 ADR 拍板前，代码 = `62ef617`），不是现状。
> 现已不同：facade 的 `invalidate` / `invalidate_by_kb_version` **已改为真委派** `get_cache("federation")`
> （前者按 key 精确失效、后者改上下文 + `invalidate_namespace` 递增租户 epoch，见 `semantic_cache.py:127-143`），
> `L3Cache` 所在的 `applications/agent_federation/agent/cache/layers.py` 已随 Stage 2 删除。
> 下面各行保留原样，因为它们是**决策依据**，不是当前事实陈述。

按全仓 grep 实测（`git grep` 范围内的调用方，不含定义与自调用）：

- `L3Cache`：只有定义（`applications/agent_federation/agent/cache/layers.py:222`），**零调用方**；
- `SemanticCache.invalidate` / `invalidate_by_kb_version`：只有定义（`applications/agent_federation/agent/cache/semantic_cache.py:127-143`；本批重写后现位，原引 :158-173 已漂），**零外部调用方**；`invalidate_by_kb_version` 仅打日志，并未真正失效任何东西；
- `NullCache`：真被 `SemanticCache.get/set` 使用（`applications/agent_federation/agent/cache/semantic_cache.py:75-78,120-123`），是联邦轨真实能力；
- L1 精确命中与 TTL：真能力，但整层依赖 Valkey；连不上时 `_get_valkey` 返回 None，**静默 no-op**（`applications/agent_federation/agent/cache/layers.py:27-49`）。
- 联邦自己的 `applications/agent_federation/docs/audit-report.md:101,107` 把 L3 与「KB 更新自动失效」标 ✅，但全仓 grep 只有定义与自调用（`L3Cache` 零调用；`SemanticCache.invalidate*` 零外部调用）⇒ **台账写的能力比代码多**，这也是收敛前必须先纠正的证据面。
- 反向漂移同样存在：`docs/architecture/agent-harness-capability-map.md:189,354` 仍把 PG 轨写成「空租户串 → 全局无过滤命中（跨租户可读）」的 P0 风险，但代码已于 2026-10-23（commit `6381b70f`）改为空租户直接 miss（`packages/agent-runtime/agent_runtime/cache.py:53-55`）⇒ 台账既有「比代码多」，也有「比代码旧」；Stage 5 必须以代码为准逐行重读，不得照抄台账。

复核命令（可直接重跑，范围均为 `git grep` 的版本控制清单）：

```bash
git grep -n "L3Cache" -- ':!docs' ':!*.md'                   # 仅 layers.py:222 定义
git grep -n "invalidate_by_kb_version" -- ':!docs' ':!*.md'   # 仅 semantic_cache.py:168 定义
git grep -n "CACHE_ENABLED" -- ':!docs' ':!*.md'              # 两处 config + main_agent:481/511/531 裸读 + 测试清理
```

⇒ 联邦轨宣称的 L1/L2/L3/失效四层里，**L3 与失效是纸面能力**；真正可保留的是 L1 精确命中、TTL、Null 负缓存。C 不是把这些能力留在两套实现里，而是：在唯一 Valkey 实现里把 L1/TTL/Null 做实，把失效做成真实实现（命名空间 epoch + 精确 key 删除），把 L3 直接删除（零调用方，不保留纸面层）；PG 侧模块、SQL 与测试随实现退役。

### 2.4 联邦侧 PG 池的附带发现（不属于本 ADR 的决策面）

`applications/agent_federation/api/server.py:82-84` 调用 `await init_pool()` **不传 DSN**；而 `packages/agent-runtime/agent_runtime/db.py:21-37` 对空 URL 明确返回 None（内存模式）。`applications/agent_federation/agent/db.py:4-6` 的 docstring 却声称「池 URL 取 `AGENT_PLATFORM_DATABASE_URL`」——当前只是 re-export（`:17-21`），没有读 env 的包装。⇒ 在当前代码下，联邦的类型化记忆/任何 `get_pool()` 调用都拿不到池，除非另有模块以 URL 初始化。**这是独立的接线缺口，已立 #146。C 下缓存不再依赖联邦 PG 池，因此 #146 不再是缓存切换的前置；它仍是联邦类型化记忆的前置，按自己的排期修，不与本 ADR 捆绑。**

## 3. 问题定义：真正坏的是什么

| # | 问题 | 证据 | 为什么"改默认值"治不了 |
|---|---|---|---|
| P1 | 一个 env 名两种相反默认值，且有三处绕过 config 对象 | `applications/agent_server/config.py:44` True vs `applications/agent_federation/agent/cache/config.py:16` False；`applications/agent_federation/agent/main_agent.py:481/511/531` 直接 `os.getenv("CACHE_ENABLED","false")` | 改默认值只让两边数值相等，绕过仍在，语义仍按 app 分叉 |
| P2 | 命中路径的隔离保证不一致 | PG：恒带租户谓词 + 空租户 fail-closed（`packages/agent-runtime/agent_runtime/cache.py:53-60`）；联邦 L2：无 filter、mapping 无租户（`applications/agent_federation/agent/cache/layers.py:169,209-214`） | 把联邦默认改成 true 会把 #133 的跨租户命中面打开；改成 false 则继续保留一条不可用的路径 |
| P3 | 能力差集没有契约，且部分差集是纸面能力 | PG 缺 L1/TTL/负缓存；联邦 L3/失效零调用（§2.3） | 不决定"哪套是唯一实现"，就无法定义哪些能力必须补、哪些可以丢 |
| P4 | 只有半层收敛，没有全局装配与门禁 | `packages/agent-core/agent_core/cache/base.py:4-7` 只统一 key/统计；两套读法（模块函数 vs 类）并存；无 lint 阻止第三套 | 默认值统一后仍可能出现第三套，且无人能靠门禁发现 |
| P5 | 两条轨里只有一条真的在部署 | k8s 仅 agent_server；k8s 无 Valkey 实例；联邦未部署（`deploy/k8s/20-agent-platform.yaml:24-25`，`docs/operations/minimal-release-runbook.md:520,539-540`） | "统一到 true"会启用一条在现网根本不存在的路径；"统一到 false"会关掉唯一在跑的缓存。C 的答案是**补生产部署 + 补开发/测试 Valkey**，不是改默认值 |

**回答"是不是系统架构存在问题"**：是。问题不在"有两个文件"，而在于平台对"缓存正确答案"的定义有两份——隔离谓词一份有、一份无；时效与失效一份无、一份是纸面；默认开关一份真、一份假。`CACHE_ENABLED` 的默认值冲突只是这个分裂的显影剂。

## 4. 选项

| 选项 | 做法 | 代价 / 风险 | 结论 |
|---|---|---|---|
| **A 双轨并存 + 显式边界** | 保留两套；修 #133（L2 加租户 tag/filter 或显式 silo 断言）；配置按 app 命名空间拆分；文档写清能力差集；加门禁禁止第三套 | 成本最低；但长期维护两套、两种命中语义、两套测试；仍不满足"单一实现"，#134 只能改成"两个诚实的名字" | 否决：两套定义长期并存 |
| **B 收敛到 PG 轨** | 在 `agent-runtime/cache.py` 补齐 L1 / TTL / 失效 / 负缓存；加 app scope；联邦委托 PG | 需要一次迁移、联邦 PG 池接线、embedding 维度检查；PG 的 ANN/淘汰/资源隔离需按量级评估 | 否决：PG 仍与事务库共享资源，无法独立扩容；不满足生产级目标 |
| **C 收敛到 Valkey 并退役 PG（选用）** | 一套契约 + 一个 Valkey 实现；生产与开发/测试都连 Valkey；补齐 L1/TTL/负缓存/真实失效/租户过滤/fail-open/健康/部署；删除 PG 缓存模块、SQL、测试与表 | 开发/测试需要 Valkey（Docker 或本地二进制）；新增一个状态型基础设施与运维面；集群化前要验证 Valkey Search 的集群语义 | **选用**：单一实现、单一语义；用户明确要求开发测试也用 Valkey |
| **C2 单一生产轨 + PG 开发/测试适配器** | 一套契约 + 两个适配器；Valkey 生产、PG 开发/测试；契约双跑 | 两适配器有漂移成本；需要长期维护 PG 侧 L1/TTL/负缓存/失效；开发/测试与生产不同引擎，问题发现时机不同 | 否决：用户 2026-10-25 明确改为「开发测试也用 Valkey，而不是 PG」；保留 PG 适配器与 C 的单一实现目标冲突 |

## 5. 为什么是 C

1. **它正面回答"生产级"**：生产目标的缓存必须能独立于事务库扩容、必须有确定的淘汰与 TTL、必须能在不拖垮 OLTP 的前提下承受查询峰值。Valkey 的 TTL/淘汰、内存索引、单线程命令模型与独立资源池，天然满足这三条；PG 的缓存表只会和业务表争同一组连接与同一块磁盘。
2. **PG 轨即使补到"能跑"，也不是生产级缓存**：当前 PG 路径无 ANN、无 TTL/清理、写侧无界、与读共用 20 连接池（§2.1）。补 HNSW 与背压后可以在 100/s 包线内工作，但它的容量上限由事务库决定，且缓存写入会挤占业务查询的连接；这不是靠改参数能消除的架构耦合。
3. **Valkey 的"能力"必须先做实，才能当生产件**：当前联邦轨 L3 零调用、失效只打日志、L2 无租户 filter、客户端不在镜像、连接失败永久 no-op、compose 用 `noeviction`（§2.1、§2.3、§7）。C 的第一原则是**不把现有 Valkey 代码直接打开**，而是按契约重写实现并补齐隔离、失效、fail-open、健康与部署。
4. **单一实现消除适配器漂移**：C2 要求同一份契约在 PG 与 Valkey 上双跑，但两个引擎的命中语义、TTL 行为、并发模型并不相同；长期维护两套实现会让"契约通过"变成新的维护负担。C 只保留一个实现，契约测试直接面对真实 Valkey，开发/测试与生产走同一条代码路径。**代价是开发/测试需要 Valkey**：用固定镜像的本地 service 承接，缓存无关的单测显式关闭缓存；这是用户明确选择接受的成本，不再用 PG 适配器换取零依赖。
5. **它消除 #133 而不是绕过 #133**：Valkey 实现的 L2 查询恒带 `tenant`/`scope`/`kb_version` TAG 过滤，空租户在入口 fail-closed；旧的无 filter 查询随 `layers.py` 退役而消失。
6. **集群路径是真实的，但不必现在做**：所有缓存查询都以 `tenant` 为第一隔离维度，因此集群化可以按租户分片，单次查询只落一个分片，不需要跨分片全局 KNN；这使"单节点先跑、量上来再集群"有可执行的演进路径。**前提是先在目标版本上验证 Valkey Search 的集群支持**（§6 Stage 6、§8），不能把"理论上可分片"当成已验证。
7. **满足 AGENTS.md 三层判据**：单一契约在 `agent-core`（零依赖）；唯一适配器与工厂在 `agent-runtime` 统一装配，应用不得自行 new 后端；`scripts/lint_architecture.py` 增加"Valkey 客户端只能在适配器内、应用不得裸读 `CACHE_ENABLED`、不得出现第二套缓存实现、生产清单必须 `CACHE_BACKEND=valkey`、禁止 `CACHE_BACKEND=pg`"四类门禁。
8. **回滚与迁移成本可控**：缓存是优化不是正确性依赖。不迁移 PG 历史缓存；Valkey 冷启动就是全 miss；生产故障时回滚动作是"关闭缓存"或回滚镜像，**不是切回 PG**。PG 表在停止读写并经过一个生产发布周期后删除，删表前不依赖它做任何回滚。
9. **为什么不是 C2**：C2 的 PG 适配器不是"免费保留的开发体验"，而是一套需要补齐精确命中/TTL/负缓存/失效/隔离测试的第二实现；两套实现长期并存会重新制造本 ADR 要消除的分裂。用户已明确否定 PG 作为开发/测试后端，C 是与其决策一致的终态。
10. **为什么不是"都统一为 false"**：agent_server 的 true 是根 `.env.example:110` 与 `README.md:408` 的已文档化行为，也是唯一在跑的缓存；改成 false 是净能力回退。**为什么不是"都统一为 true"而不先收敛**：那会把一条无实例、L2 无隔离的路径打开，且默认值相等并不等于契约相等。**为什么不是 B**：B 能把能力补齐，但把生产缓存继续绑在事务库上；用户已明确目标不是 demo 级，而是可独立演进的生产级。

## 8. 复审触发条件（出现即回来重看本决策）

1. 单节点 Valkey 持续内存 > 60%、或 2× admission 包线下 lookup p95 > 10ms、或 p99 > 25ms ⇒ 启动 Stage 6 集群评估（先验证 Search 集群支持，再谈分片）。
2. 目标 Valkey Search 版本不支持集群/跨分片 KNN，且按租户路由也无法满足容量 ⇒ 另立 ADR 评估专用向量层；不得退化成无租户过滤的全局 KNN。
3. 出现第三个语义缓存消费者或第三种命中策略（精确/语义/检索结果混合之外的策略）⇒ 先补契约与门禁，再谈实现。
4. 联邦获得请求级租户身份（不再是进程级 `TENANT_ID` silo）且需要多租户行级隔离 ⇒ 隔离面必须重算（本 ADR 的 tenant TAG 设计需重新评审）。
5. 两个 app 的 embedding 模型/维度出现不可调和的差异 ⇒ 保留"同契约、按模型分索引"，并重评是否需要共享 Valkey 实例。
6. Valkey 因其他原因成为平台级共享基础设施（限流/会话/队列）⇒ 资源归属、SLO、故障域与容量模型重新评审。
7. 业务要求缓存持久化或跨重启热缓存 ⇒ 重新评估 AOF/PVC/复制；当前明确选择"可冷启动"的缓存语义。
8. 出现第二套缓存实现或 PG 缓存复活（代码、配置、清单任一）⇒ 先修门禁，再继续功能开发。
9. 开发/测试环境无法稳定运行真实 Valkey，测试开始系统性 skip 或改用假实现 ⇒ 重审测试策略与 CI 资源，不得把 skip 当通过。
