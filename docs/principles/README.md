# 工程方法论（用户拍板的开发约束）

> 来源：用户 2026-11-18/19 在日常反馈中反复强调的几条指导规则，2026-11-19 提炼成文并由用户确认入库。
> 定位：这些是**行为约束**，不是建议。AGENTS.md《AI 开发范式》有指向本文件的指引，开工前应读。
> 每条都附「原话锚点」和「可操作判据」——判据要能机械判断，不靠自觉。

---

## 纲要（最高原则）：产品功能设计必须站在用户视角

**原话**（用户 2026-11-20）："产品功能设计要站在用户视角去考虑。"

**这是统摄以下所有 P 条的最高原则**——P1–P5 是它在具体场景的展开。任何功能设计先过这一关，再谈实现。

**判据**：
- 设计一个操作前，先问：用户看到这个界面/按钮/提示，会**以为发生了什么**？和实际发生的一致吗？
  - 反例（本次踩过）："下线"操作成功了但文档还显示在列表（实际没丢、检索也不召回了），用户却以为"没成功"——因为 UI 没站在用户视角呈现真实状态。
- 操作的**可用条件**要从用户的心智出发，不是从后端能力出发：
  - 正例（用户拍板）：删除按钮只在文档**已下线**时才出现——用户不能一步误删有效文档，删除是两阶段操作的第二道。
- 提示文案要说"用户能懂、且与实际一致"的话，不暴露内部术语（REVOKED/假灯）当作用户消息。
- 判断一个功能好不好，标准是"用户要不要重新学一遍"——需要记忆负担的设计就是失败的设计（呼应 P3）。

## P1 · 一次改动 ≠ 一个点，而是一类问题

**原话**："不是简单改啊，你还要考虑一些其它的情况。"

**判据**：
- 修 bug 前先问：这是孤立的点，还是某一类问题的第一个实例？
- 复现测试：同一根因能否用不同问法/不同数据/不同入口复现？能 ⇒ 是类，必须修类不修点。
- 收尾前列出"本次改动影响的全部分支/调用点"，逐一确认，不许只看眼前那条路径。

**反例**（本次犯过）："知识图谱问不到"只盯着缓存，实际根因是路由 prompt 没告知有知识库——同一问题在"关系抽取""远程监督"上都存在，是类不是点。

## P2 · 配置与代码分离，运行参数必须可热变更

**原话**："提示词能作为配置嘛，不是写死到代码里的那种，我改了提示词不用再重启服务。""从全局治本角度去考虑解决，难不成以后我改个提示词就要重启一次？？？"

**判据**：
- 任何"运营中会调整的东西"（prompt、阈值、词表、开关、字典）不许硬编码进源码。
- 统一检验：**改这个东西需要重新构建/重启吗？** 需要 ⇒ 它是被误当代码的配置，必须外置 + 热加载。
- 热加载要有可测判据（如文件 mtime 指纹 + 回归测试），不能只"外置到文件"却用 lru_cache 锁死（反例：route_hints.json TD-7）。

## P3 · 全局统一靠机制，不靠自觉

**原话**："我希望的是整个平台样式风格统一、操作统一，不要让用户有更多记忆负担，这是做产品的思路。"

**判据**：
- 跨多个页面/模块的一致性，靠**单一实现 + 全局装配 + 门禁强制**三层，缺一层即退化为约定。
- 判断信号：如果一致性靠"每个地方记得写一样"维持，就是反模式——迟早破窗。
- 局部对齐（把一个页面改成和另一个一样）不算"统一"，只是"碰巧一致"，没有机制保证。

**欠账标注**：本次只在知识库页做了局部对齐（选中态照搬会话列表），未做全平台审计 + 单一实现 + 门禁。待用户拍板补。

## P4 · 先理解意图，再决定约束层级（边界先行）

**原话**："选库只压 direct，不压 sql/search。"

**判据**：
- 加规则前先问：这条规则的作用域边界是什么？什么情况下**不该**生效？
- 避免"为修 A 把 B/C 也改了"的全量覆盖。
- 落实：`apply_kb_scope` 只拦 direct，其它 route 原样放行——边界先行，不是无脑覆盖。

## P5 · 事实先于方案，取证先于动手

**原话/行为**：用户多次要求"自己测一遍、查样式"，反感只跑门禁就交差；每次我实取后才找对根因。

**判据**：
- 任何"我以为是 X"都要用命令证伪：SSE 帧 / DB 读数 / 日志 / DOM / 真浏览器截图。
- 禁止"看起来像"就动手改。取证问题的输入要语义新颖（否则命中缓存/复用旧结论，拿到假证据）。
- 视觉/交互问题必须真浏览器渲染确认，typecheck/lint 只查结构不查渲染。

## 元原则（纲要统摄五条）

> **纲要：产品功能设计站在用户视角**——功能好不好，看用户要不要重新学、看到的和发生的是否一致。
>
> 在此之下，五条指向同一件事：**用工程手段消除"重复的人力负担"**——
> 用户不该重复学习不同页面的操作（P1/P3），
> 开发者不该为改一个 prompt 重复重启（P2），
> 系统不该为同一根因重复出 bug（P1/P5），
> 改动不该产生意料外的副作用（P4）。

一句话：**把"靠人记得 / 靠人重复做"的事，变成"机制保证 / 一次配置"的事；而这一切的出发点永远是用户视角。**
