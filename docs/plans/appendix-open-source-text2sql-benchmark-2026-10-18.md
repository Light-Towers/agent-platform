# 附录：开源 Text-to-SQL 项目定向调研（2026-10-18）

**范围**：Chat2DB、SQLBot、WrenAI、Vanna、DB-GPT 五个与 nl2sql-service 同域的开源项目。
**方法**：公开渠道检索（许可证原文、仓库快照、第三方实测）；未运行任何项目、未逐行读码——本文所有能力描述均来自公开文档与实测报告，标注"宣传口径"处需自行核验。
**结论先行**：五个项目**无一可整体集成**进 agent-platform 对外服务（许可证或架构原因，见 §2）；全部定位为**设计参考**。调研最重要的产出不是"抄什么"，而是三个改变内部判断的事实：① 开源 Text2SQL 的**权限层全域盲区**（闭源或付费），反证 §5.9 三层纵深与平台租户计划不可替代；② **WrenAI MDL** 是 P1-6 语义层的现成终态参照，比自造 DSL 更稳；③ 我们的 §5.11 三分类异常反馈闭环在开源里**没有对标物**，是自研增量。

**方法论结论**：外部参考到此为止，不改内部架构分叉。之前"等 Q25 拍板再引用"的判断成立——五个项目的许可证形态恰好说明，**这个赛道没有可白嫖的成熟企业级实现**，收敛只能靠自建。

### 3.1 深读：五个设计的根因 → 我们的差距 → 落地（2026-10-18 补充）

§3 清单回答"做什么"，本节回答"为什么值得做"。五个设计收敛到同一第一性原理：**把语义、验证、边界从 SQL 执行里拆出来显式化，不让 LLM 一口气猜完全程**。

#### D-A. 多轮指代消解与上下文继承（DB-GPT 最被低估的设计；我们的现状是四层全空）

- **根因**：问数产品 80% 的真实使用是多轮追问——"那上个月呢""按城市拆一下""**上述**销售额最高的三个城市，它们的复购率是多少"。单轮 pipeline 每轮重新理解问题，就丢了上轮实体、时间窗与已确认 SQL。
- **设计**：DB-GPT 三件明确写进文档的能力——表别名自动延续、指代消解（"上述…它们"→继承结果集实体）、口语时间转 SQL（"最近一周"→`DATE_SUB`）。SQLBot 的"历史对话检索"（历史问答对进 RAG）与 Vanna 错题回流是同一思想的不同切面。
- **我们的现状（2026-10-18 逐个实读，四层全空）**：契约层 `session_id` 字段在（`shared_schemas/query.py:21-25`，"对话状态隔离"语义）；消费层 nl2sql `api/`+`services/` 全目录 grep 零命中（请求进来不读）；状态层 `DataAgentState`（`agent/state.py:6-24`）纯单轮字段无历史槽位；节点层 `extract_keywords.py:22-38` 只处理当前 query。⇒ nl2sql 今天是**无状态单轮服务**，"那上个月呢"会被当作独立问题重新理解。
- **落地**：方案 §5.13（M1–M6 契约 + 验收 16–18）。

#### D-B. 知识与模型解耦（Vanna / DB-GPT 共识；直击 Q18 死结）

- **根因**：语义知识（DDL/文档/范例）是长期资产，LLM 与 embedding 都会换代——绑死就等于换代=全库重灌。
- **设计**：Vanna"换 LLM 不丢 training"（知识在向量库，LLM 只是读者）；DB-GPT SMMF 把模型管理层与知识层分离。
- **没人说的细分（对我们要用的部分）**：换 **LLM** 不丢（prompt 是文本）；换 **embedding** 必须重建向量——五项目无一解决。唯一出路是分层：**原文层**（模型无关、永久）+ **向量层**（可重建派生）。
- **我们的现状一半对一半错**：YAML 元知识库=原文层（✓）、meta 向量=派生层（✓）；但 Q18 的 1536 vs 1024 未定，选错一次=全库重灌。
- **落地**：Q18 答案方向=YAML 事实源 + 向量派生 + 灌库幂等可重跑（P0-2 接住）。

#### D-C. 推荐问题与追问生成（WrenAI；产品层）

- **设计**：新对话从最相关表生成 3 个候选问题；每答生成追问。
- **价值**：问数产品冷启动（用户不知道能问什么）+ 可回答域的自文档化。
- **落地**：登记为产品项（P2），nl2sql 只暴露"基于指标清单/linkable 白名单生成候选问题"能力，交互落上层；不占 P0/P1 资源。与简历口径"内含可回答文档"同思想。

#### D-D. 列注释的人机协同修订入口（Chat2DB"自定义 AI 数据集"；不依赖被搁置的 MDL）

- **设计**：用户给列标注含义，AI 据此大幅提升理解。
- **为什么独立成活**：不依赖表间关系声明（被搁置项）；且对我们双重价值——① 列注释是 LLM 理解列语义的最强信号，比类型信息重要一个量级；② 我们的注释现在自动从 `information_schema` 抽取，正是 S-8 二阶注入源——开受控人工修订通道 = 用审核过的注释替代自由文本，**效果与安全是同一件事**。
- **落地**：S-8 修法第三选项；meta 知识库"列语义修订"入口 = P1-6 组件。

#### D-E. dry-plan / dry-run 治理原语（WrenAI）

- **设计**：dry-plan（展开 SQL 不执行）/ dry-run（连真实库只验执行计划、不返回数据）——把"语法+计划"验证与"数据"执行解耦。
- **落地**：作为 §5.8-C8 降级链新一环——打源超时 → dry-run 只验计划 → 退字典，多一道不花钱的保险。我们的对应物（字典校验 + EXPLAIN 自校验）已有雏形，缺的是成型为"一个原语、两种模式"。

#### D-F. 反向确认：我们的流水线形态在开源里是什么水平

Chat2DB 把"链式推理分步解答"（拆解需求→分步验证→生成）当 **3.0 宣传黑科技**，而我们的 LangGraph 12 节点从一开始就是显式分步 + 条件边 + trace 可观测。**开源产品 2026 年才营销的形态，是我们的起点**——面试口径可用（"节点化可观测流水线 vs 同期开源的单体 prompt/刚宣传链式"）。

## 4. 对 Q25（第二条 Text2SQL 路）的输入

外部证据进一步支持**收敛而非并存**：

1. **同范式证据**：Vanna 三件套（DDL/documentation/question-SQL）、SQLBot 知识库（术语/示例/提示词）、WrenAI 上下文层（MDL/instructions.md/queries.yml）——三个独立项目收敛到同一形态。仓内 `agent_server/sql/schema_store.py` 的三件套正是 Vanna 形态，与 nl2sql YAML 元知识库**差异只在载体（PG 表 vs YAML 文件）与流水线长度**，不是两种架构。
2. **Vanna 的终局警示**：该范式的最流行开源实现已归档并转向"治理能力收费"——免费开源撑不到企业级，**平台不能把终态押在任一外部项目上**；反过来，自建收敛后的语义层是我们的资产而非负债。
3. **WrenAI 给出的收敛后形态参照**：语义层（MDL，可审查可版本化）与执行层（治理原语 + 只读）分离——与我们 §5.12.1 归属表"语义层统一 store、执行层共用 guard + 只读账号"的划分同构。Q25 拍"收敛"时，可直接引用本节作为外部同构证据。

**仍未答**：Q25 本身是拍板项（收敛路：nl2sql 退化为 `agent_server/sql/schema_store` 的 builder 之一），本文只提供证据，不代替拍板。

## 5. 开源盲区：权限与多租户（本次调研最重要的负面发现）

| 能力 | Chat2DB | SQLBot | WrenAI | Vanna | DB-GPT |
|---|---|---|---|---|---|
| 多用户/工作空间隔离 | 商业版 | 开源有隔离，**权限规则闭源** | 未见开源实现 | 2.0 付费 | RBAC（schema 白名单） |
| 表/列级权限 | 商业版 | **闭源 xpack** | 未见 | 付费 | 有（schema 级） |
| 行级权限（RLS） | 商业版 | **闭源 xpack** | 未见 | 2.0 付费 | 未见 |
| 字段脱敏 | 未见 | 未见 | 未见 | 未见 | **有** |
| 审计日志 | 商业版 | 部分闭源 | 未见 | 付费 | 有 |

**三条结论**：

1. **§5.9 三层纵深的必要性有了外部佐证**：五个项目里"脱敏 + 表级 + 行级"三样齐全的仅 DB-GPT 一家（且框架重、许可证虽好但引入即替换）；SQLBot 把最核心的权限做成闭源二进制；Vanna 把治理能力全部划入付费线。**"LLM 够不着的第一道（账号 GRANT + 视图）"没有开源同侪可抄，只能自建**——这不是我们的过度设计，是赛道现实。
2. **面试/简历叙事增量**：被问"Text2SQL 数据权限怎么做"时，可答"调研过五个主流开源方案，权限层要么商业版要么闭源，所以自建三层纵深"——有据可查的差异化，且本附录即证据。
3. **对平台租户计划的意义**：租户/工作空间隔离是同一盲区（SQLBot 的工作空间隔离开源、但其行级规则闭源）。`plan-platform-tenant-workspace-identity-2026-10-18.md` 的 L1/L2/L3 边界不需要因外部项目调整。

## 6. 自研增量：异常反馈闭环无对标物

开源最好水平是 Chat2DB 的"SQL ERROR 一键修复"（**人工在环**：用户点一下才把错误送回模型）与 3.0 宣传口径的"生成时自检自查"（营销表述，非执行反馈）。**没有一个项目实现 §5.11 的"先机器分类、再决定喂不喂模型"三分类自动闭环**（可纠正→correct 回路 / 可改写→带改写目标 / 不可纠正→拒答不烧钱）。MAC-SQL/CHESS/ReFoRCE 等研究的执行反馈模式与我们的设计方向一致，但开源产品化层面是空白——这坐实了 §5.11 是自研增量，也意味着没有外部测试基准可抄，验收判据（§5.11.3）必须自建。
