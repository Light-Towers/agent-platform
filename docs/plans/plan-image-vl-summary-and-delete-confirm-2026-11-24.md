## 0. 两个问题（实取）

### 问题一：知识库图片"没有语义"，问答靠 alt 文字触发，模型看不懂图

现状（实取 `node_md_img.py`）：
- 图片摘要功能**代码有、开关默认关**（`IMG_SUMMARY_ENABLED` 默认 false，`:450-454`）→ 历史切片的图片 alt 都是写死的"图片描述"，没有画面语义
- `summarize_image()`（`:147-194`）确实调 VL 模型生成 50 字摘要，但只在开关开时执行
- 摘要只对**本地 `images/` 文件夹里被 MD 引用的图片**生效（`:66-68` 扫描文件夹）——远程 URL 图片不走这条路径
- 结果：检索靠"图片描述"这几个字 + 周围正文匹配；回答里图片是 `![图片描述](url)`，模型只能说"有一条图片链接"，无法描述画面

用户拍板史：早先「图片摘要字数」案用户选 A（50 字软约束、开关另案）——但开关在生产**实际是开的**（`IMG_SUMMARY_ENABLED=true`，取证 readings.md:35），只是历史数据没重生成、且远程 URL 图片不走该路径。

### 问题二：删除操作确认机制不全

实取前端删除/下线操作：

| 操作 | 位置 | 确认 | 可逆性 |
|---|---|---|---|
| KB 库删除 | KnowledgeBaseSidebar.vue:171 | ✅ `window.confirm` | 不可逆（库下有文档时禁止） |
| 文档下线（软删） | KbUpload.vue:141 | ✅ `window.confirm` | 可逆（重新发布恢复） |
| 文档永久删除 | KbUpload.vue:179 | ✅ `window.confirm` | 不可逆 |
| **会话删除** | ChatView.vue:230 → conversations.ts:102 | ❌ **无确认** | 不可逆（后端物理删会话+历史） |

⇒ 唯一缺确认的是**会话删除**，这是个真缺口（误点即删整段对话历史）。

## 1. 方案一：知识库图片 VL 语义摘要

**目标**：让导入的图片 alt 变成真实画面语义（如"绿色边框展台设计图，带 Company Name 占位"），检索和回答都有画面信息。

### 1.1 三条路径

| 路径 | 做法 | 适用 |
|---|---|---|
| A. 开启生产开关 + 重传历史文档 | `IMG_SUMMARY_ENABLED=true`（生产已开）+ 重传带图文档 → 本地图片走 `summarize_image` 生成摘要 | 新上传/重传的本地图片文档；历史数据要重传 |
| B. 远程 URL 图片也生成摘要 | `node_md_img` 增加"从 MD 里已存在的远程图片 URL 拉取图片→VL 摘要→替换 alt" | 用户手写远程 URL 的文档（如测试文档） |
| C. 问答时对召回图片现场调 VL | rich adapter 提取图片后，对每张调 VL 生成描述再进 prompt | 不重传、立即可用，但每张图问答时都调 VL（成本/延迟） |

### 1.2 推荐：A 为主 + C 兜底

- **A**：生产开关已开，核心是**重传历史带图文档**（一次性），让本地图片文档的 alt 变成语义摘要。零新代码。
- **C 兜底**：对"召回的图片 alt 仍是'图片描述'占位"的历史文档，问答时在 adapter 里对图片现场调 VL 生成描述注入 prompt（限最多 2 张、带缓存，避免成本爆炸）。这样历史文档不用重传也能"被看懂"。
- **B 不做**：远程 URL 图片是少数场景（用户手写 URL），且拉远程图有 SSRF 面，不值得。

### 1.3 关键约束

- VL 端点：KS 用 `api.siliconflow.cn`（Qwen3-VL-8B），agent_server 的 C 路径也要用独立 `VL_BASE_URL/VL_API_KEY`（已在图片全链路方案配好，复用）
- 摘要字数：50 字软约束（`image_summary.prompt`），用户早先拍板不动
- C 的缓存：按图片 URL 哈希缓存摘要（避免每次问答重调 VL）， TTL 可配
- C 的成本：每轮最多 2 张、失败静默降级为原 alt（不拖垮问答）

### 1.4 影响面

- A：仅重传操作，无代码改动
- C：`rich_answer_adapter.py`（提取图片后调 VL）+ `config.py`（开关/上限/TTL 配置）+ `.env.example` + 测试

## 2. 方案二：删除确认机制

**目标**：所有不可逆删除都有二次确认，且确认文案说清后果（用户视角：用户看到的与发生的一致）。

### 2.1 改动

唯一缺口是**会话删除**（ChatView.vue:230）：
- 在 ChatView.vue 的删除按钮点击处理加 `window.confirm`，文案说清"永久删除该会话及全部对话历史，不可恢复"
- 与现有 KB 删除确认风格一致（`window.confirm` + 说明后果）

### 2.2 改进（可选，P2 全局统一）

现在 4 处删除确认都是各自 `window.confirm` 字面量（散点，违反 P3）。抽一个共用 `confirmDestructive(title, detail): boolean` 工具（web/src/utils/confirm.ts），4 处统一调用：
- 好处：文案风格一致（"不可逆/可恢复"标识统一）、以后加"输入名称二次确认"只改一处
- 代价：小重构，4 个文件各改一行

推荐：先补会话删除的 confirm（必做）；工具抽取随带做（小、符合 P3）。

### 2.3 影响面

- ChatView.vue（会话删除确认）
- 可选：`web/src/utils/confirm.ts`（新）+ KbUpload.vue / KnowledgeBaseSidebar.vue 改用

## 3. 验收

1. 上传带本地图片的文档（重传）→ chunk 里图片 alt 是语义摘要（非"图片描述"）→ 问画面相关问题能命中并回答
2. 历史"图片描述"文档 → 问答命中图片时 C 路径调 VL 生成描述 → 回答含画面信息（缓存命中第二次不再调）
3. 会话删除点击 → 弹确认，取消不删，确认才删
4. 全前端门禁绿 + 相关单测
